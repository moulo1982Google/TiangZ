# Numeric派生计算基准

## 环境

- 日期：2026-08-01
- 系统：Windows 11 Pro 10.0.26200
- CPU：Intel Core i7-13700F，16核24线程
- 构建：Rust `--release`
- 参数：10,000 Entity，500ms预热，2,000ms正式窗口，5轮取中位吞吐

## 结果

| 场景 | 来源写入/s | ns/来源写入 | 派生重算/s | ns/Entity周期 |
| --- | ---: | ---: | ---: | ---: |
| 普通属性写入 | 53,492,061 | 18.69 | 0 | 18.69 |
| 单来源写入并重算 | 17,345,316 | 57.65 | 17,345,316 | 57.65 |
| Base/Add/Pct分别写入 | 18,294,456 | 54.66 | 18,294,456 | 163.98 |
| Base/Add/Pct批量写入、重算一次 | 34,271,573 | 29.18 | 11,423,858 | 87.54 |

## 结论

- 单次派生写入约为普通写入的`3.08`倍，但绝对成本只有约`58ns`，不构成当前优化优先级。
- 连续修改三个来源时，当前单字段API会重算三次，约`164ns/Entity`；批量一次重算的理论上限约`88ns/Entity`，可节省约`46.6%`。
- 普通业务继续使用清晰的`numeric[type]`单字段写法。只有战斗结算等同一逻辑点会集中修改多个来源，并且真实Profile显示Numeric成为热点时，再增加粗粒度批量op。

## 边界

本基准复用正式Runtime的派生公式内核，并模拟`HashMap<u32, i64>`值表与dirty revision；不包含V8 Fast op、线程本地Store借用、handle校验、protobuf、AOI、Gate或Socket。因此它用于比较计算策略，不代表完整业务调用吞吐或服务器容量。

复现命令：

```powershell
npm run perf:numeric -- --entities 10000 --warmup-ms 500 --duration-ms 2000 --rounds 5 --json
```
