# AOI Grid 密度矩阵 2026-07-30

## 固定口径

- Windows IOCP，1 MapHost、16 Gate、1 Login、1 LoginMgr、1 Location。
- Rust全链路客户端；每玩家5Hz Move、1Hz MapProbe；服务端20Hz。
- 每5条Move保持同一方向，Bench速度1 Cell/s；玩家从Grid中央Cell开始闭合移动。
- Setup并发16，地图每Tick放行1人；全员入图后排空15秒、预热10秒、正式窗口60秒。
- Bench关闭每玩家100ms自动回血，隔离Move、AOI和Probe。

## 判断

1. 地图相对Grid原点生效：10、15、20边长分别准确占用100、225、400个Grid。
2. 扩大空间显著减少AOI可见关系；3000人从10x10到20x20由703,682降至187,008。
3. 3000@20x20的移动编码平均约0.43ms，说明AOI编码已不是唯一瓶颈。
4. 当前3000人产生15k Move/s与3k Probe/s。即使降低空间扇出，ActorLocation入站及其队列仍会产生超时。
5. 下一步性能工作应分开建立“Move消息”和“Probe RPC”两条曲线，定位18k/s中请求响应链的固定成本；不能继续用扩大地图掩盖入站瓶颈。

## 拆链路复测

| 场景 | Map CPU avg | 吞吐/延迟 | 背压与过载 | 判断 |
|---|---:|---:|---:|---|
| 1000人，10×10，纯Move 5Hz | 68.2% | 5,000 Move/s，159,376 Push/s | 0/0 | AOI完整链路稳定 |
| 1000人，10×10，纯Probe 1Hz | 6.7% | 1,000 RPC/s，p95/p99 1.23/3.37ms | 0/0 | 低频RPC成本很低 |
| 1000人，10×10，纯Probe 15Hz | 37.3% | 15,001 RPC/s，p95/p99 3.44/4.45ms | 0/0 | ActorLocation RPC不是18k/s失败根因 |
| 3000人，10×10，纯Move 5Hz | 103.0% | 14,997 Move/s，331,632 Push/s | 2,475/20,787 | 超出持续容量 |
| 3000人，15×15，纯Move 5Hz | 143.0% | 15,004 Move/s，365,756 Push/s | 7,540/40,070 | Audience批次碎片化加重 |
| 3000人，20×20，纯Move 5Hz | 205.0% | 15,005 Move/s，351,539 Push/s | 6,379/36,469 | Audience批次碎片化成为主瓶颈 |

扩大世界虽然降低可见关系，但把接收者拆成了更多小Audience。10×10到20×20时，Gate batch约从21,739/s升至87,019/s，每批接收者从14.84降至4.04。当前实现中每个Rust Audience batch都会由TypeScript单独调用`transport.Send`，再按Gate拆内部消息；下一轮优化应把同一逻辑Tick的多帧按Gate合并后一次发送。

## Tick级按Gate聚合后

| 世界 | Map CPU优化前/后 | 内部过载优化前/后 | 背压优化前/后 | Push/s优化前/后 |
|---:|---:|---:|---:|---:|
| 10×10 | 103.0% / 83.9% | 20,787 / 17,023 | 2,475 / 2,774 | 331,632 / 357,675 |
| 15×15 | 143.0% / 86.6% | 40,070 / 2,001 | 7,540 / 3,535 | 365,756 / 494,359 |
| 20×20 | 205.0% / 91.4% | 36,469 / 0 | 6,379 / 3,797 | 351,539 / 524,416 |

Core现在把同一逻辑作业整体交给Transport，正式SceneTransport再在同步Tick尾把多个作业按Gate重组为一条内网批量消息。客户端frame没有合并，Gate仍按各组接收者扇出。结果证明此前的反向CPU曲线主要来自Map到Gate内部消息碎片；聚合后稀疏世界的CPU成本已显著收敛。三个3000人点仍有入口背压，不能作为保守容量承诺。
