# 0.7 连接断开后的迟到响应

2026-09-26 实施前契约。Scene 仍存活，但 RPC 的来源连接已经断开时，业务 Promise 可以继续完成；框架不能假装它已经取消，也不能把它从热更在途计数中提前移除。不过迟到结果不能再排入该来源的出站队列，更不能在 Disconnect 清理后重新插入连接 ID 编码缓存。

目前短期 Disconnect tombstone 只在入站帧检查中使用，既有 Scene 析构保护也不能代表单个连接已经失效。响应需要保存与其等待期间绑定的连接状态：收到断线即失效，生命周期不依赖墓碑的 30 秒寿命或容量淘汰。同号连接的后续新等待属于新状态，旧 finally 不得删除/终结它；不同连接相互隔离。

本步只约束框架的迟到 RPC 响应排队与引用清理，不取消业务、不撤销已执行事务、不保证业务恰好一次，也不把编码大小宣称为堆总内存。维持已有 ordered/unordered 调度、断线业务回调和 Session 清理顺序。真实任务仍在途直到原 Promise 结束。

先以 ordered/unordered、超过 tombstone 寿命、同号新等待和不同连接做反例；再使用真实 V8/网络断开及指标观察补充完整生命周期矩阵。新增状态按运行中等待拥有，最后实际完成或来源失效时去掉索引，不能用永久 tombstone、清空所有队列或缩短业务等待绕过问题。此修改与一般 TS mailbox 总量、二进制保留预算分别记录。

修复只为实际异步入站等待维护来源状态；同一连接的多个等待共享引用计数，最后结束核对对象身份再删除索引。收到 Disconnect 立即使原状态失效并删除索引，旧 Promise 仍拥有失效状态直到真实结束，墓碑到期不能复活它。Scene 析构清理索引，原 mailboxClosed 保护保持。同步响应仍检查当前墓碑。异步单向 Handler 也可能持有来源索引，但不产生响应时不会增加迟到响应计数。
