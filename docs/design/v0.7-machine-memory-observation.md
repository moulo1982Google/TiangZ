## 解释所依据的官方口径

- [Docker WSL 文档](https://docs.docker.com/desktop/features/wsl/)说明镜像构建后 Linux 页缓存可能继续占用较多内存，WSL 的自动回收功能用于把空闲内存归还 Windows。它支持当前解释，不能代替本机具体历史归因。
- [Docker stats 文档](https://docs.docker.com/reference/cli/docker/container/stats/)说明 Linux CLI 会减去部分缓存；本机是 cgroup v2，减去的是 `inactive_file`。因此 stats 较小不能推导整台 WSL 内存很小，不能只累加容器 stats。
- [Linux proc 文档](https://cdn.kernel.org/doc/html/latest/filesystems/proc.html)区分 Cached、AnonPages 和估算可用的 MemAvailable；[cgroup v2 文档](https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)区分层级内存统计和消亡中的子组。
- 本机 WSL 为 2.7.14.0，没有用户 `.wslconfig`。当前 [Microsoft 配置文档](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)列出的默认 `autoMemoryReclaim` 是 `dropCache`，因此不能声称“没配置文件就是关闭回收”。回收为何尚未把这些页归还主机，本次没有确证。配置需要在 WSL 启动时生效，不能为诊断直接重启正在长稳的共享 WSL。

## 留档与后续观察

本次文件均在 `temp/v0.7-memory-diagnostic-20260927/`：`samples.jsonl`、`sample-summary.json`、`capture-report.json`、`cgroup-inventory-r2.json`、`environment.json`。短采样已正常结束；独立观察器每 60 秒记录一次 Windows 可用/提交/进程分组、WSL 缓存/匿名页/压力和 Docker stats，跟随原协调器身份，终止后退出，最长 72 小时。它只提供诊断，不修改原长稳资格或故障窗口。

活动入口为 `monitor-r2.json`、`monitor-r2-process.json`、`monitor-r2-samples.jsonl`。需要处理观察器时核对 PID、创建时间、可执行文件、脚本路径和 SHA，不按进程名停止。首版观察器在未发生运行失败时主动替换：把睡眠期限的两次时钟读取改成单次剩余时间计算，避免边界负值。只停止这一个新建的只读观察器；原文件、替换前状态和已采样记录保留，R7 协调器、Host 和存储未中断。

取证中的两个探针失败也保留：WSL 多层 `sh -c`/awk 参数转义导致退出码 1、空结果；修正为向 `wsl --exec sh -s` 的 stdin 传完整脚本后取得真实值。不能把失败的空结果当作零。WSL 根 cgroup 没有 `memory.current`/`memory.events`，根部使用 `/proc/meminfo` 与 `memory.stat`，具体运行容器再读其 memory.current/events；缺失字段不改报零。

当前 Windows 仍有约 12 GiB 可用，采用持续只读观察。没有强制 GC、清页缓存、停止无关容器或改变 WSL 内存上限；这些操作会改变当前实验环境。若后续匿名内存、提交量或不可分页池持续增长，应依据新趋势定位对应进程/驱动；若需要调整 WSL 预算或回收策略，在明确的维护窗口执行并重新记录环境资格。本次没有运行 codegen、重编产品或重复产品测试，验证是实际系统采样、已有长稳资源证据核对及观察器语法/首份真实样本检查。
