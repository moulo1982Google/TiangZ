## 解释所依据的官方口径

- [Docker WSL 文档](https://docs.docker.com/desktop/features/wsl/)说明镜像构建后 Linux 页缓存可能继续占用较多内存，WSL 的自动回收功能用于把空闲内存归还 Windows。它支持当前解释，不能代替本机具体历史归因。
- [Docker stats 文档](https://docs.docker.com/reference/cli/docker/container/stats/)说明 Linux CLI 会减去部分缓存；本机是 cgroup v2，减去的是 `inactive_file`。因此 stats 较小不能推导整台 WSL 内存很小，不能只累加容器 stats。
- [Linux proc 文档](https://cdn.kernel.org/doc/html/latest/filesystems/proc.html)区分 Cached、AnonPages 和估算可用的 MemAvailable；[cgroup v2 文档](https://cdn.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)区分层级内存统计和消亡中的子组。
- 本机 WSL 为 2.7.14.0，没有用户 `.wslconfig`。当前 [Microsoft 配置文档](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)列出的默认 `autoMemoryReclaim` 是 `dropCache`，因此不能声称“没配置文件就是关闭回收”。回收为何尚未把这些页归还主机，本次没有确证。配置需要在 WSL 启动时生效，不能为诊断直接重启正在长稳的共享 WSL。

诊断口径：

- 内存提示线为 Windows 或 Linux 可用内存低于各自总量 10%、Windows 提交量达到提交上限 90%、或 Linux memory PSI 的 some/full `avg60` 达到 1%。这些是本机调查触发值，不是产品 SLA 或新的长稳合格线；文件缓存总量大本身不触发“影响测试”。
- 性能提示检查 Host 最近五分钟吞吐中位数是否低于此前基线 80%；DBProxy 正常区间阶段均值是否同时超过此前区间均值中位数两倍、增加超过 250 ms，且当前至少有十次操作、基线至少五个区间。少量样本或粗粒度均值不能证明尾延迟无异常。
- 原始数据库计数仍遵循冻结故障窗口。直方图只对同一节点、同一进程代次求差，整个采样区间必须与故障/恢复窗口无交集；重启代次不相减，故障错误不混入正常负载基线。内存压力不能成为把正常窗口错误移入故障窗口的理由。
- 内存样本过期、阶段不匹配、观察器失败或负载进度陈旧记录为未知，不写成正常。Windows page reads 包含文件读入，不能单独等同 swap；同时出现压力和性能/错误异常也只表示需调查，不能直接断言因果。

- Windows 子进程继承管道，短启动器 exit=0 后 Node close 仍未触发。实际三秒子进程复现为 409 ms exit、3770 ms close。原内存 worker 已采样成功，所以只接管它并核对身份、新样本；没有另起重复内存采集器。独立启动器应使用文件承接长期 worker 的 I/O，并分别监督启动器退出和 worker 就绪；普通负载仍须排空输出，不能一律以 exit 代替 close。
