# 0.7 远程 Host 操作的共享准入

本批基于 `292258e`，处理 HostSceneTransport 的未提交共享队列，独立于本地 Scene/Actor/Spawn 名额和原生调用期限。旧 Node 探针已接受 65536 个 send 后又接受一个 call，提交 **65537** 项；Rust 整批解码上限为 65536，因此后来的项能使此前接受的整个批次失效。证据 `temp/v0.7-host-operation-admission-audit.json` 仅记录实际 TS 打包，未发网络，后续必须另验真实宿主。

## 接受与拒绝

直接采用已有 Rust 格式限制：一个未提交批次最多 **65536** 项，包含 call/send/sleep；含 4 字节批头、每项 17 字节元数据与 payload 的打包总成本最多 **64 MiB**。call/send 每帧 **2..1048576** 字节，sleep 无业务帧但仍消耗元数据。等待回复的 call/sleep 另有既有 **65536** 项上限，单向 send 不持有回复名额。不是将两种所有权相加为唯一业务请求总数。

先验证输入帧，再检查需要的 pending 名额、共享条数和打包成本；未通过时不分配等待记录、不注册新路由、不入队。数量/字节拒绝使用有类型的 SceneOverloaded(1011)，保持公开 Scene.call/send 的已有错误映射；无效输入保持调用失败语义。RPC/sleep 返回拒绝 Promise，send 同步拒绝。同步路由建立失败不影响已有队列或等待者。

每项保存接受时的帧长度与打包成本。借用的帧在交付后不得修改；若到 flush 时帧已经失效或长度改变，只拒绝/丢弃该项，并记录无效帧，保留其他项的原顺序与等待者。该检查不声称检测同长度内容修改。批次成功交给 Rust 后，TS 排队成本归零，等待回复的名额仍到真实完成/提交失败/停机终结时释放；原生包副本继续由原 Rust 预算持有。提交失败必须有聚合计数，不能把首次 send 接受解释为可靠送达、自动重放或取消对端执行。

原生 deadline 刷新与取消使用已有独立路径，不混入远程批次数量，也不能因远程队列满额而失去释放能力。sleepHost 的计时/远程执行期限起算问题、本地与网络 TS 二进制保留、Rust 批次间并发上限仍另行定义，本批不改变其时间语义。

## 观测与验证

固定 Process 指标分别给出未提交条数/打包成本、pending 回复数、三个上限、三类容量拒绝、无效帧与提交失败。不将 queued bytes 叫作 V8 堆上限，不将待回复数叫作所有远程在途工作。Core/宿主桥观测改变需完整构建重启，无新用户配置、Native schema 或编译规则；两个 VS Code 插件保持版本，AI 指引和实际分发同步。

先保留混合 send+call/sleep、刚好满批/满字节、非法帧污染旧批次的失败反例；再验证公开 1011、pending 与 queue 的独立回收、路由/提交失败、停机、借用帧失效仅影响本项。旧 mock 若使用 Rust 从未允许的一字节业务帧，应修正夹具并保留原 ID/完成断言，不能放宽原生格式限制。实际 V8 使用正式生成协议，确认拒绝与原已接受工作、恢复及指标；最后含 KCP 完整矩阵、Linux 条件编译和实际 AI 归档验收。没有发布操作。
