# 0.7 Spawn 的进程总量准入

2026-09-26 实施前冻结。前一批已保证同步准入失败不残留计数；本批约束 `scene.Tasks.Spawn`，不把它宣称为全部 TS mailbox、业务 Promise 或堆内存的预算。

保留现有每 Scope 256 项，并新增同一 ProcessHost 合计 4096 项硬上限。4096 沿用现有 EntryScene unordered 并发量级，相当于 16 个满额 Scope；这是可验证的短任务防护边界，不是吞吐或内存容量结论。未新增部署字段、关闭开关或无限值。完整基线和真实 V8 满额/恢复用例须通过后才保留此默认值。

已接受但尚未开始的微任务、执行中的 Promise、Scene 已销毁或取消但实际尚未结束的任务都占用额度。拒绝发生在创建 record/watchdog/任务微任务前，以 `RpcError(SceneOverloaded)` 明确失败，body 不执行。原 Scope 上限错误也保留原文字并使用相同错误码；名称/body 等输入错误不归类为过载。

额度归属于原 ProcessHost，不查当前全局 Runtime。成功后记录高水位；Timer/ID/记录创建等同步失败退回本次额度，不抬高成功高水位。真正完成时恰好归还一次，归还先于可抛错的附属清理；取消、注销 Scene、超时和重用 Scene ID 不能提前释放。旧 Runtime 的迟到完成不能扣减新 Runtime 的额度。准入只同步拒绝，不创建等待队列，也不自动重试任务体。

沿用 Scene→SceneContext→ProcessHost 的所有权桥，内部 hook 标为 `@internal`，不增加业务侧预算操作 API或新管理层。Process 层快照和固定 process 标签指标报告当前值、4096 上限、成功高水位和拒绝次数；每 Scope 的 256 上限继续由 Scope 执行。前一批 retired Scope 的生命周期持有与真实完成回调保持。

验收先运行失败反例，再实现：跨 17 个 Scope 的总量竞争、原 256 上限、Timer 注册失败回滚、注销仍占用直到实际结束、同 ID 重建与 Runtime 重建隔离，以及真实 V8 通过正常 RPC 拒绝第 4097 项、释放后恢复、热更窗口仍能推进。不得用缩小任务数、增大上限、吞错或取消后立即减计数迁就测试。两份 AI 入口及三端分发同步，完整生命周期矩阵包含 KCP。开发版未冻结 Stable 声明锁；此 Model/Core 变更需要完整构建和重启。
