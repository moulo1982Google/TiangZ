# AI 开发规则、工程检查与领域复用设计

> 状态：2026-10-13 需求方已明确“请继续推进直到完成”。P0/T1/T2 已交付，T3/P1 与游戏试点持续实施；分组只表示实现顺序。实际结果、首轮失败与发布锁核对见实施计划；源码、分发、客户端加载与 AI 行为成绩分别登记。

## 1. 目标与范围

本设计源于苟道三国近期的玩家数据、建筑、集市、英雄、兵营、兵阶与编队开发。目标是减少重复接线、让确定性错误提前失败，并明确 AI 建议、检查结果与运行时保证各自的边界。

交付分四部分：

1. AI Plugins：补充可跨游戏复用的设计判断、触发条件、证据要求与正确检查入口。
2. TiangZ 工具：将真实 Model 导出验证前移；复用现有协议、配置、Native 与类型检查，完善合并后检查和诊断。
3. 游戏试点：强类型领域登记、公共事务装配与测试夹具复用；先在苟道三国验证，不直接进入 Core。
4. 验收与效果记录：按证据层级选择测试，记录有效工时、返修原因和接入改动范围。

本轮设计不提出改变 mailbox、网络、热更、DBProxy 事务或 Rust Runtime 语义。Core 改动为 Model 校验错误增加上下文；现有合法/非法判定保持不变，不增加 Stable API。完整剩余实施现已获准；后续依赖安全补丁及内部声明图锁审查单独登记。

## 2. 已确认与设计假设

### 已确认

- 先做完整设计，何时动工由需求方决定。
- 需要明确哪些内容进入 AI Plugins，哪些由代码、检查工具和测试负责。
- 当前讨论的目的为提高开发规范性、减少错误与重复工作。

### 本设计选择

- 通用检查由声明宿主执行，编辑器只调用与展示，插件不获得编译、数据库或安装能力。
- 复用当前检查、生成器与测试驱动；只补已证实的缺口和覆盖不足。
- 玩家领域复用先在游戏内落地，验证后才能另行提出框架推广。
- 不将开发期清库、单次功能通过、代码行数或提交频率当作开发效率/生产可靠性的证明。
- 不安排日期或承诺百分比收益。先采集可比较数据。

下文保留设计阶段的选择与基线，实际结果以实施计划和验收矩阵的后续记录为准；发布和正式客户端安装不由代码检查结果代填。

## 5. AI 规则设计

### 5.1 输出要求

每条新增/修订规则包含：触发条件、应作的判断、禁止的绕过、权威文档、所需检查/证据、无法自动证明的部分。技能入口只保存短决策与引用，详细案例放引用文档。默认只读取任务相关主题，不把完整手册重复复制到每个入口。

规则号在 [validation-matrix.md](validation-matrix.md) 中用于追踪本设计；开工时先与现有规则目录核对。下列拟定 ID 尚未注册，不是可调用的当前 API。

| 拟定 ID | 触发与规则正文要点 | 自动化边界 |
| --- | --- | --- |
| `model.export-shape` | Model 对外导出须符合实际宿主校验。Map/Set 可作为实例字段，不作为导出值；冻结不会改变原型。执行真实入口预检 | 工具验证实际值；AI 不维护第二套判定 |
| `protocol.post-merge` | 新增/修改协议分支合并后，无论 Git 是否冲突，都在最终合并树执行声明宿主协议检查与目标 SDK 检查 | 不赋予 AI 手改生成物或静默重分配已有编号的权限 |
| `persistence.no-change-identity` | 无领域变化仍先处理 pending，再按该操作契约检查指纹/历史回执；不能把“值相同”当作“同一操作” | 是否需要 durable no-op 回执由业务定义；不能强制所有 no-op 写数据库 |
| `persistence.domain-integration` | 新领域明确加载、格式/配置校验、规划、记录写入、回执、恢复、视图与副作用；每个持久字段唯一归属 | 登记与类型覆盖可查；经济规则需受控测试与评审 |
| `validation.target-execution` | 源码测试/编译不等于目标宿主或客户端实际运行。跨端推算验证双方共享参数与真实样本 | 不自动调用浏览器/服务；不把 Creator 某次问题泛化到所有客户端 |

以下复用/修订现有规则，不另起同义 ID：所有权/Actor 形态、Model/Hotfix、结果未知与原字节重试、操作预算、在途生命周期、证据分层、包身份。mailbox 建议要保留两种正确方案：适当独立控制 Scene，或 unordered + 按业务键锁；同一玩家写入可继续 ordered。不能全局把 ordered 改成 unordered。

### 5.2 跨入口一致性

- 通用规则在权威文档定义一次；Codex/Claude 技能共享同源，Cindy 按可支持的范围更新对应规则。
- 如需要让三个 MCP 工具返回新增规则，修改 Developer Tools 的 design-core `rules.ts` 与对应 patterns；调用者参数与返回结构保持当前契约，不把需要项目状态的结论伪装成纯设计工具已检查。
- 增补 `check.mjs` 的缺规则、重复 ID、失效引用、平台路径泄漏与分发一致性检查。
- 字符串存在测试只证明打包；另保留场景评估，检验 AI 是否真的读规则并调用正确入口。
- 不增加 Cindy/MCP 的文件写入、网络、编译或安装权限。设计工具默认保持只读。

## 6. T1：真实 Model 导出预检

### 6.1 入口与加载路径

拟新增 `tools/check_module_model_exports.mjs`，并接入 `checkGameProject`：生成检查 → 类型/Program 检查 → Model 导出预检 → 现有可选 Native check。CLI 子命令拟支持 `--modules-dir`、`--host-profile`、`--json`；公共 `npm run check` 行为为检查，不自动修复。

预检读取当前模块目录、依赖图、真实入口与宿主 Stable Core，使用与构建一致的解析/边界逻辑。必要时把 `build_runtime_bundles.mjs` 的解析器提取为共享内部 helper，先独立验证构建输出不变。

临时 bundle 只装配模块 Model 登记和真实 `sealGameModules`，不运行完整 ProcessBootstrap、Scene onStart、配置运行初始化或 Hotfix。子进程单独隔离注册表，验证完整预期模块图和公共 API 依赖，禁止用手写 `defineGameModule` 桩或只检查少数常量代替。

### 6.2 判定语义和错误信息

- 调用真实 Core 判定，保留原错误前缀；内部诊断拟附 `moduleId`、`exportPath`、失败原因、来源文件（有可靠源码映射才附行号）。
- `copyModelExports`、嵌套 `collectModelObjects` 原有规则保持：顶层 undefined 非法；数组/普通对象递归；symbol/accessor 非法；循环对象按 visited 终止。
- 当前实现将 function 当作终端，不在本批擅自收紧成“仅可 new 的函数”；文档中“构造函数”与实际更宽判定须说明边界。
- 必须在读取属性值前检查 descriptor；不执行 getter；同一共享对象路径按稳定遍历第一次出现位置报告。
- 新诊断为 `tiangz.model.invalid-export`；加载异常为 `tiangz.model.load-failed`；环境缺失为 `tiangz.model.check-unavailable`。诊断仅增加上下文，不增加公共玩法错误码。

### 6.3 Native 与执行边界

Native 构建指纹、worker 绑定只能来自当前生成声明，不从正则全盘扫描猜测未知全局。检查桥为生成器已声明的 worker 提供普通对象形式的只读占位绑定；调用 `call/drain/stats` 均明确失败，不能伪造返回结果。指纹标记为检查环境值，报告 `nativeExecutionVerified: false`，不证明真实二进制身份。

如果 Model 顶层需要真实 Native op、未声明全局或宿主初始化，预检返回 unavailable/失败，不自动造空值、跳过模块、启动宿主或降级成功。真实宿主验证仍为独立验收层。首批必须证明 Starter、Native 示例与游戏当前真实 Model 的支持范围，不能在已知消费方不可检查时直接开启默认门禁。

检查会执行受信任项目的顶层登记代码。独立子进程不是安全沙箱；编辑器自动实时分析和未信任工作区不得执行它。受信任项目须保持顶层纯声明/登记，工具自身不启动数据库/服务。对恶意顶层代码不能宣称阻止任意 IO。超出支持范围先报告，不扩展为隐式宿主执行。

资源设计：每次 CLI 操作最多一个 Model 子进程，默认 30 秒总期限、输出上限 4 MiB；超时必须回收其进程树，未确认回收则失败并记录。只清理自己创建的临时目录；源、锁、SDK、项目 dist 的字节与修改时间不变。

## 7. T2：协议与生成物检查接入

继续以 `codegen_module_protocol.mjs --check` 为完整协议权威入口；该入口已调用单模块校验、全局 ownership、staging 生成和发布比对。补充合并反例和冲突双方信息，不另建独立编号分配器。

合并流程为：形成待合并树 → 正式生成/更新的显式操作（确有需要时）→ 在最终树执行 `check` → 游戏目标 SDK/配置副本检查 → 提交与证据身份一致。CI 检查只验证，不更新锁、发布或提交生成物。

发现撞号后，由生成器与开发/Release 政策决定处理；只能处置本分支尚未发布的新条目，已有/已发布编号保留。不得自动删除所有锁、回收墓碑或改业务字段名绕锁。本设计不新增锁替换开关。

需要覆盖同模块两条不同 key 同号、跨模块冲突、完全无文本冲突的合并结果、预留 Core 编号、重复条目、无协议模块与合法多人并行分配后的重新生成。合法序列不能因跨端生成副本而被误认为多条消息。

现有配置/Native check 和游戏 `client:check`/`config:check` 继续执行。宿主不猜测客户端路径：只有当前项目明确的同步目标才检查副本。未配置客户端目标报告不适用，声明过目标而文件缺失则失败。

配置 README 也参与指纹是当前机制；本批不顺带更改哈希覆盖范围，诊断说明哪些输入变动、应运行哪个正式生成入口。

## 8. T3：检查与验收编排

不新增一个“检查全部系统”的框架。扩展已有 `checkGameProject`、测试矩阵和 `test_step_runner.mjs`，复用阶段总期限、子进程所有权与输出上限。

结果记录至少包含：格式版本、输入树/源码身份、host/project/modules、依赖解析身份、每步命令/工作目录/起止时间/退出码/实际用例数/诊断/输出摘要、未执行原因。状态区分 passed、failed、unavailable、timed-out、aborted、skipped；unavailable 或 skipped 不能充当通过。现有 JSON 接口保持原版字段，只在相应入口作兼容增补。

本批不需要为全文日志创造数据库或常驻监控。报告位于执行者显式指定或工具自己创建的任务目录，不能改变业务生成指纹或永久写入个人路径。计划选择见 [validation-matrix.md](validation-matrix.md)。

IDE 复用声明宿主的静态 worker 显示实时诊断；真实 Model 加载只由用户/CLI 显式执行。AI MCP 保持设计建议，不新增执行测试的入口。CLI、IDE、AI 文案对 unavailable 的解释一致。

## 9. G1：游戏领域登记与事务装配

这是拟定的游戏试点设计，实施不属于 TiangZ 默认框架改动。

### 9.1 类型与生命周期

在游戏 Model 声明封闭 `PlayerDomainKey`、记录/规划/视图类型映射与稳定方法签名。领域清单只导出可通过 Model 校验的冻结数组/普通对象，登记唯一名称、存储键及依赖；不放实例、Map/Set、运行中的服务或 Hotfix 闭包。

实际领域适配与方法实现放 Hotfix，通过 PlayerDataUnit/Component 访问状态。适配表按调用构造或绑定正确所有者，不保存模块级可变注册表，不把热更行为闭包永久缓存到 Model。新方法签名或字段按 Model 规则重启；不以该重构获得在线迁移能力。

先加完整性断言：九领域各有 codec、Load/Verify/Restore/PlanInitial、请求写入、回执映射、Apply、Snapshot/Push 与事实处理（无某能力显式标识不适用）。用强类型 mapped type + `satisfies` 暴露缺项；业务能力不同的领域保留特定方法。

### 9.2 事务约束

保持当前记录 schema/version、namespace、key、编码字节、写入顺序、回执和协议字段。迭代顺序来自显式冻结列表，不依赖对象插入顺序或反射扫描。新领域接入时顺序由游戏设计决定。

改前后对照使用同一受控 lordGid、操作号、初始记录、时间与随机序列；真实重启对照比较持久字段及允许变化的运行期身份，不把新进程 InstanceId 变化误判为存档变化。对照夹具固定输入，不依赖当前墙钟巧合。

保持 Change 顺序：已完成操作核对 → pending 原字节恢复 → 当前状态规划与错误次序 → 如确无写入，执行该操作的回执契约 → 一次 CommitRecords → 同步 Apply/记住结果 → 原顺序事件与推送。

- 多领域扣费/发奖保持整组原子；领域规划不改权威组件。
- 同编号同内容、同编号不同内容、旧回执与新无变化操作保持既有回复。
- 不把所有 no-op 改成持久写入；不把所有领域空计划自动推广为编队专有回执规则。
- 结果未知保留原操作号、时间戳、随机结果与载荷；不在重试时重新生成。
- 已销毁对象不 Apply/Push；已提交事务不因断线被伪装成取消。
- 保留错误次序、日志、副作用数量和幂等边界，不借拆分改玩法规则。
- 提交后事件目前不是 durable outbox；如未来业务要求持久订阅，另出消费幂等与恢复设计。

拟新增游戏 `PlayerDomainRegistry.ts`（Model 类型/登记）和 `PlayerDomainAdapters.ts`（Hotfix 实现），调整两个 Store 与玩家数据编排。具体拆分以完整设计允许的职责为限，不制造逐函数文件或只转发一层。

先通过九个既有领域无语义变化的回归；随后用下一个单独获准的新领域验证接线减少。不得为本试点自动启动科技或宝物玩法。进入 Core 的门槛是另一独立游戏/领域模式也证明相同契约；本设计不预先批准推广。

## 10. G2：测试夹具与失败场景

共享测试准备放游戏 `tools/test-support/player-domain-fixture.mjs`。公共装配默认加载真实 Model 与真实 codec，明确哪些 Host 依赖由测试桥提供；纯规则测试只导入规则函数。桩用于受控 Store/Transport/时间/随机注入，不复制领域业务或把所有依赖替换为假对象。

状态、缓存、模块注册、随机序列及注入参数属于每个用例/子进程，不全局共享。新增领域主要登记一次公共装配；某用例主动缺组件测试仍使用显式反例，不能被公共夹具自动“修好”。

所有适用的资产变更操作覆盖：普通成功、提交前拒绝、提交后回复丢失、结果未知原字节恢复、重建历史回执、同号异内容、no-op 与 pending、await 期间销毁。涉及随机的操作另外证明未重抽；计时玩法另外证明离线截止与幂等领取。

跨端验证使用真实服务端产生样本与真实客户端消费逻辑，受控迟到成功/失败都覆盖。Creator/浏览器演练由游戏选择，不放入 TiangZ 通用插件自动执行。
