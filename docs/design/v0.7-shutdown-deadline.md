# 0.7 停机期限的独立资源

本批基于 `f12b6cf`，处理 ProcessBootstrap 的停机 watchdog。当前代码先执行 runtime.stop，再把 sleepHost 加到普通远程操作队列；队列满额会立即拒绝计时操作，过早进入终结路径，未满额时计时又可能排在原生 256 个普通操作后面。本地 RPC 已有独立原生期限，但直接复用其满额后不执行 factory 的包装器会跳过停机，不能这样迁移。

## 所有权与失败语义

每个 isolate 单独预留 **1 个停机期限资源**，不占本地调用的 65536 个期限资源或远程批次/回复名额。复用现有 Deadline 的绝对到期、取消和实际最后引用归还；不创建第二套计时系统。未跨宿主刷新即结束时同步关闭资源，已经启动的原生 waiter 必须真实退出。普通业务不能使用这份停机预留，用户配置、Model/Native schema 和 Stable API 均不增加入口。

同一轮并发 stop 调用共享一个 Promise、一次 runtime.stop 和一个期限资源。保留启动尚在全局 ID 准备时收到 stop 的既有阻止发布语义，不用停机合并来放过尚未完成的启动。正常路径先预留专用期限，再执行 stop；超时保持原错误文本，不能声称已取消运行中的业务。

若专用期限创建仍异常，runtime.stop 必须执行且被观察；等待其真实结束后报告创建异常，若 stop 同时失败则保留两者为 AggregateError。此异常回退期间由既有 Rust `stopTimeoutMs + 1000ms` 外层 drain 截止时间兜底，不用普通队列、无限重试或业务 Timer 重造 watchdog。该回退不是独立 TS 环境的有限时间保证，也不能把未完成的 stop 记为成功。

停止后的 flush/cancel 终结顺序保持；onStop 自己发起的业务 RPC 仍遵循普通准入，专用期限不能为业务绕过过载。该修改不改变远程普通操作的排队期限，不允许期限到达提前归还真实业务任务，进程最终销毁仍由原宿主监督路径负责。

## 实施与验证

先以真实 ProcessBootstrap/HostSceneTransport 加可控的 Native/lifecycle 替身保留失败反例，覆盖提前成功/失败、满远程队列、并发 stop、超时和取消实际退出、期限创建失败仍执行清理、双重失败与启动中 stop。Rust 验证独立预留只有一项、最后引用归还、不改变本地调用容量，并在隔离真实 V8 子进程中验证普通期限满额时仍可创建/等待/释放停机期限。随后完整重建、含 KCP 矩阵、Linux 条件编译与 AI 实际归档验证，记录真实 Process 正常停机证据；确定性替身与真实宿主证据分别报告。

修改只涉及已有桥接/期限所有者及 Bootstrap，不为每个函数新建文件。两个 VS Code 插件无新配置/生成/编译规则需要跟随；AI 指引需说明专用预留、共享 stop 与创建失败仍清理，继续保留独立版本。没有推送、发布或用户服务变更。
