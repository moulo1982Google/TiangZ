# 2000 人单服连续 30 天：前置条件与验收设计

记录日期：2026-10-04。状态：未来实际游戏压力测试的设计备忘，尚未实施、尚未启动，不构成当前 0.7 DBProxy 验收的新门槛。用户已确认当前只完成 DP 本身的完整性、可靠性、长稳与通用性能；真实 SLG 业务接近完成后另行安排。本页保存预判、代码检查事实和待办，不修改正在运行的冻结计划、产品制品或保护业务。

## 1. 先固定“单服”和“不停机”的含义

- 单区服是业务边界；一个区服可能包含多个 Process、Scene、DBProxy 节点和存储实例。必须记录完整拓扑，不能把区服数当成进程数，也不能将多个 TS 线程的能力算给一个 Process。
- 如果目标是游戏主 Process 连续运行 30 天，记录机器启动代次、PID、进程启动时刻、启动 ticks、制品 SHA 和版本。自动拉起、主备替换或重启以后在线恢复，属于可用性验证，不算原进程连续运行。
- 正式计时从 2000 个账号完成业务初始化、负载达到约定速率后开始，以单调时钟累计至少 2592000 秒。预热、部署、重连未就绪及故障恢复时间不能擅自补作负载时间。
- 正常连续运行与故障恢复分别定义资格。若允许强杀 DP/PG/Redis，列出允许变化的组件和代次；游戏主进程“不重启”的门禁继续独立执行。故障期错误保留，不能以“注入过故障”为理由豁免窗口外错误。
- 冻结源码、可执行文件、SDK、配置、schema、种子、负载、资源上限、故障计划及门禁。运行中修改候选不能继承修改前的资格时间。

## 2. 2000 个连接必须产生可测量的业务负载

使用真实模块、协议、鉴权、玩家初始化和持久化路径；完成进入区服的账号才计入业务就绪人数。2000 条空连接、客户端心跳或只调用 DBProxy 不能代替 2000 名 SLG 玩家。

在启动前说明在线存量与行为到达率：同一批账号长期在线，同时有独立的登录、断线、重连、离线及新旧账号轮换群体。固定账号可发现状态累积，轮换可发现 Session、Actor、Component、Timer、订阅和异步任务的释放问题。加入真实比例的生产/领取、建造、行军、查询、交易、联盟与热点争用，记录请求大小、读取命中率、事务写集、广播扇出和单位数量，不能用平均小 DTO 代表全部业务。

需区分固定并发的闭环负载与固定到达率的开放负载：闭环机器人等待上次响应后才发下一次请求，服务变慢时实际压力会自动降低。按业务目标选择模型，报告计划到达、实际发送、完成、失败、超时、未发送和负载机遗漏，保留延迟直方图及端到端等待时间。负载机饱和、延迟遗漏或就绪人数不足是无效证据，不能靠减少实际请求率取绿。[k6 到达模型说明](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)。

负载机与目标进程分别观测 CPU、内存、网络、句柄、队列及时间误差；目标机器资源预算覆盖游戏、DP、PG、Redis、日志、监控和备份。不能直接将当前 2C4G/100 人合成 DP 负载线性外推为真实 2000 人容量。

## 3. 把持续增长算到第 30 天和收尾

以下只是量级示例，需以实际业务行为替换，不能作为已测容量或吞吐承诺：

| 假设 | 连续 30 天的量级 | 对设计的影响 |
| --- | --- | --- |
| 2000 人，每人每秒 2 次请求 | 4000 次/s，10368000000 次请求 | 计数宽度、延迟采样、请求日志和负载工具预算 |
| 每请求记录 200 字节日志 | 2073600000000 字节，约 2.0736 TB，未计压缩或保留策略 | 日志轮转、远端归档、索引和磁盘写入 |
| 每人每分钟一次确认的普通直接持久化写入 | 86400000 次写入及相应幂等回执 | 回执 payload、索引、claim、WAL 与备份增长 |
| 每人每 30 秒产生一个不可变事件 | 172800000 个事件 | Outbox、Stream、消费进度和最终全量核对 |
| 稳态持续泄漏 100 KB/min，KB 按十进制计算 | 4.32 GB | 小斜率也需量化，不能只看瞬时内存充足 |

区分逻辑请求、RPC、记录、事务、事件、重试和物理字节，不将数量混算。用代表性 payload/写集测量每种表的表、索引、TOAST 字节及维护后的增量，记录 PG WAL/复制槽滞留、备份/归档、Redis AOF/RDB、日志、原始证据、临时文件、inode 与最终报告的额外空间。旧轻量样本的每条字节数不能移植给真实存档。

至少以多个完整日窗口估计增长和剩余可用天数，覆盖备份与 AOF 重写峰值、最终全量对账、失败归档及必要预留。提前固定预警/停止阈值和可执行的归档方案；每日正常容量下降必须被发现，不能等到磁盘满或 inode 耗尽。数据库大小观察默认只读，不能为了让图表变平删除权威数据、裁原始门禁证据或任意清幂等回执。

### DBProxy 回执和事实保留的已知边界

目前普通确认写入留下幂等回执，部分回执保存原始 payload/写集。已交付的是 [D4 只读容量观测](../../../TiangZ-DBProxy-0.7/docs/capacity-observation.md)，[删除与回执保留稿](../../../TiangZ-DBProxy-0.7/docs/record-deletion-and-receipt-retention.md)仍未实现；没有通用自动 TTL 或清理保障。

未来需先定义操作号退休、结果未知重试期限、离线/备份恢复后的旧请求、旧客户端和分区延迟、墓碑/拒绝栅栏或归档回执查找，再选择保留方式。删除回执后相同操作号可能重新执行业务，不能直接执行“清理 7 天前的数据”。已发布 Outbox 也不代表下游已消费，账本事实和消费历史的责任另行界定。本页不授权删除、迁移、协议变更或自动归档。

## 4. 资源回收要检查实际引用与生命周期

分别观察 TS/V8 heapUsed/heapTotal、external、ArrayBuffer、自然 GC 后的低位与停载低位；Rust 堆、allocator 保留、各进程 RSS/PSS；cgroup anon/file/kernel/dirty/writeback、swap/OOM；线程、文件描述符、Socket、连接池、mailbox、等待任务和订阅数量。文件缓存上涨、allocator 保留或 V8 扩堆不能直接判成泄漏，active 计数下降也不能证明内存释放。[cgroup v2 内存字段](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files)。

按同一进程代次，在预热后相同比例负载和完整维护周期中比较自然低位及增长斜率；让高频创建/销毁、重连、取消、失败/结果未知重试、断线后迟到响应和允许的 Hotfix 切换分别成为有界用例。诊断快照需有 CPU/内存/暂停预算，不能在资源告急时无界抓取导致第二次故障；不以强制 GC、定期重启或清缓存维持连续运行资格。

### TiangZ TimerSystem 的静态保留路径

当前 [TimerSystem](../../app/core/runtime/TimerSystem.ts) 的 `Cancel` 从活动 Map 删除定时器，但不移除 heap 中的 `TimerEntry`；`__update` 只弹出已到期堆顶。长延迟 Timer 被取消后，堆节点及其 callback/onCancelled 引用可能保留到原到期时刻。`Count` 返回活动 Map 大小，因而 `Count = 0` 不能证明取消节点已释放。这是源码确认的保留路径，尚无本次运行复现、业务泄漏规模测量或修复，不能把它当作当前 DP 云上失败的原因。

未来长稳前增加专门的创建/取消远期 Timer、所有者销毁及重复替换用例，观察 heap 节点、回调引用和自然回收，确定合理的物理清理/压缩方案。修复必须保留取消通知至多一次、原所有者 mailbox 顺序、在途回调直到真实完成才释放、同轮新 Timer 不重入及重复 Timer 跳过遗漏次数的语义；不能仅把计数归零、删除在途引用或禁止业务取消来绕过。

## 5. 时间与编号要跨越长期边界

- 进程时长、I/O 期限用单调时钟；持久化活动截止、日志和日历结算使用约定的服务器墙钟。校时、倒退、暂停、跨日/周/月、时区和服务器时间恢复通过隔离时钟夹具验证，不修改共用宿主机时间。
- Node 原生 `setTimeout/setInterval` 的 delay 上限为 2147483647 ms，约 24.855 天；更大值会被调整为 1 ms。只审计实际使用这种原生 API 的工具/业务入口。TiangZ `TimerSystem` 使用 `TimeSystem.FrameTime` 的自己的堆，此上限不能直接套在它上面；业务仍使用所有者 Timer，禁止通过原生等待绕过。[Node v24.18.0 timers](https://nodejs.org/download/release/v24.18.0/docs/api/timers.html#settimeoutcallback-delay-args)。
- 在 4000 次/s 的假设下，每请求增长一次的无符号 32 位计数约 12.43 天耗尽。这只是边界示例，未证明工程存在回绕。逐项审查 RPC/连接/Timer/批次/实例号、generation、序号、offset、重试次数和采样序号，验证最后合法号、耗尽拒绝、旧号迟到以及重启恢复。现有安全整数与不复用契约不得改成截断、归零或回绕；RPC 数、连接创建数和游戏操作号的速率分别计算。
- 外部 Token、凭据、租约、证书、DNS/连接、云端及本机任务的寿命均需超过试验与收尾边界，或有已验证的正常更新路径。不能只检查启动时合法。

## 6. 容量、背压和数据正确性并行验收

采样总 CPU 与最忙业务线程、TS 延迟/长任务、p50/p95/p99/max、队列深度及最老等待、DB 连接等待/占用、PG I/O/WAL/锁、Redis 命令/AOF、网络、磁盘延迟和广播字节。单 Process 的一个 TS 业务线程可能先于机器总 CPU 饱和；平均值正常不能代替尾延迟和积压斜率。

正常、热点峰值与明确过载分别固定预期：准入拒绝是否发生在业务执行前、调用期限是否被所有等待共同消耗、超时后结果未知如何以原操作号查询/重试、断线后是否阻止旧来源重新排队响应。已接受任务的责任一直保留到真实完成，不能靠清队列或释放仍运行的配额伪造排空。故障解除后，客户端、存储超时计数、待发布/缓存修复及最老年龄须在原计划期限内共同恢复；不能只看一次 HTTP 200。

数据门禁包括资产/库存/资源守恒、交易原子性、幂等结果、快照版本、追加事实、Outbox 未发布/死信、Stream 唯一事件集合及内容、重复投递是否内容一致、消费进度与最终权威读取。维护和可恢复故障不免除数据不变量；请求可用性错误按预先声明的实际窗口归类，跨窗口指标只能判定发生区间，不补造精确事件时刻。

## 7. 正常维护必须进入日历和资源预算

- PostgreSQL：覆盖 autovacuum/ANALYZE、冻结与事务年龄、长事务/锁、死元组、索引增长、checkpoint、WAL 归档及复制槽。VACUUM 使空间可复用不代表文件立即缩小，不能用每天强制 FULL 或清表维持容量。[PG18 常规维护](https://www.postgresql.org/docs/18/routine-vacuuming.html)。
- Redis：覆盖 AOF 重写、RDB/fork、写时复制、磁盘与瞬时内存预算。重写正常完成不代表原可靠确认契约已验证；保留故障中写入确认与恢复的原始证明。[Redis 持久化](https://redis.io/docs/latest/management/persistence/)。
- 备份需要实际恢复到独立环境，核对恢复点与数据契约，不能恢复覆盖运行中的权威存储；原始试验保持连续。监控备份失败、积压、校验和恢复耗时。
- 证书/Token 更新、日志轮转及健康 timer 的 waiting/running 转换属于可预期维护。允许的变化必须精确到属性与语义；单位配置、服务身份、健康和实际失败仍严格检查，不能放宽整类保护。

维护事件进入时间线，区分“测试计划允许的维护”和异常。共用机器上的教练直聘、绯红之境继续作为保护业务，负载、诊断、备份恢复和清理仅作用于本轮明确所属资源。

## 8. 测试工具也要能运行及复核 30 天

当前控制工具已对驱动采用 JSONL 全量落盘、只保留末条/计数和分块完整报告，但这不证明所有收尾路径都有界。`independent-review.mjs` 与 Python `controller.py` 仍有整份报告读取，`reconcile.mjs` 仍收集全量事件编号；已通过的 24h 体积/30 万编号夹具只覆盖固定量级，不能代替 30 天、上亿事件、真实查询和持续分配。

正式开始前，将报告复核、SQL/Stream 分页、完整事件匹配、哈希/归档和失败取证设计成有界驻留；使用固定 high-water/序号或一致性读取点避免边读边写制造假差异。需要全量集合比对时可用磁盘索引/外部排序，但必须核对所有 ID 与内容、处理重复和中途失败，不能采样替代原全量门禁、降低采样或扩大预算取绿。循环 SQL/Redis/Lua、输出缓冲、超时、分页恢复、磁盘临时空间和最慢收尾必须实际预检。

已确认的长期配置限制：当前 memory-r4 `new-deploy.py` 为协调器配置 `RuntimeMaxSec=70h`；本机 `register-probe.ps1` 的重复期限为 4 天。它们适合当前 30→960→1440 分钟接续，但不能用于 30 天。未来新现场统一核对 controller、guard、observer、负载机、本机探测、凭据、计划文件与时钟的寿命，留出部署、空载、对账、归档和退出期限；本页不改运行中冻结设置。

每个辅助任务都绑定本轮 owner/root/plan SHA、阶段、PID/启动代次和实际制品。终态自停前先验证身份，观测缺失/采集失败报告未知或失败，不能补零。监控独立于负载生成与人工聊天，夜间有明确的故障、完成和需要人工处理通知；状态不变时静默，不能依赖本地 PC 连续开机才保证云端安全停止。持续检查监控标签是否出现 playerId/requestId 等无界基数，以及全量日志、轮询结果和未完成 Promise 的常驻累积。

| 前置事项 | 当前证据/状态 | 启动前必须交付 |
| --- | --- | --- |

| 回执/不可变事实长期增长 | D4 已有只读观察，删除保留稿未实施 | 真实字节/日增长和空间预算；需要清理时先冻结安全退休契约 |
| 控制/复核全链路有界 | 驱动已修；整报告/全 ID 收尾仍存在 | 原资源限额的 30 天量级预检，真实分页/内容匹配及收尾失败反例 |
| 控制与探测期限 | 当前 70h / 4 天 | 新现场统一寿命、失联、收尾与安全停止演练 |
| 时间/编号/外部凭据边界 | 有现行契约，30 天组合未验 | 有限边界与隔离时钟测试，耗尽/更新/迟到及恢复证据 |
| 维护、备份恢复与故障资源预算 | 本轮 DP 故障资格不能替代业务维护验收 | 覆盖一个完整维护周期、隔离恢复、恢复期限与保护业务核对 |
| 最终数据/性能门禁和报告 | 尚未冻结业务阈值 | 正常错误、数据守恒、尾延迟、资源斜率、积压与对账的明确门槛 |

先完成定向边界与收尾预检，再在冻结候选上推进 24h→72h→7 天试运行；这些是发现问题的阶段，最终仍需独立完整连续 30 天。失败修复后使用新版本、新现场和新完整计时，不拼接失败前时长；此前已经独立通过的阶段保留原版本证据。

运行中保留完整时间线、计数、窗口、资源、SQL/Stream 内容及哈希/制品身份。出现正常窗口错误、数据不变量、负载未达标、资源预留不足、业务保护失败、观测缺失或收尾失败，按预先定义策略停止本轮所属资源并保全现场；不得将未知归零、忽略第一次失败、扩大资源、放宽期限或事后修改窗口来转成通过。

最终通过需要连续负载完整时长、真实进程身份、每个允许故障的恢复、停载后的实际排空/回收观察、最终全量权威对账、原始 SHA 复核、实际退出与保护业务检查全部成立。结论绑定本次业务、种子、机器、存储与制品；不扩张成所有游戏或生产容量承诺。当前 DP 进展仍以 [控制内存与资格记录](v0.7-soak-control-memory.md) 和 [云端报告](../../../TiangZ-DBProxy-0.7/docs/cloud-fault-soak-2026-10-02.md)为准。
