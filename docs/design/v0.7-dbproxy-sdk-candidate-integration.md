# 0.7 当前 DBProxy Rust SDK 联合验收

2026-09-26。Engine `8d75f9b` 的主工程默认 Rust 依赖仍为 DBProxy 发布 tag `v0.6.2`，对应 `e9963d2e08fd64bd5c3dca04e434705a6222af83`。本批在隔离源码中显式选择 DBProxy `f25b29606b7cd77d4e1ac6da62679f4a3a658357`，检验已经实现的 SDK 请求预算与当前宿主兼容，不能用早期 16 项联调或默认发布依赖的通过代替。

## 输入与隔离

Windows 私有 Engine 源码位于 `temp/v0.7-sdk-joint-current/`，来自干净 Engine 归档；其私有 `.cargo/config.toml` 仅将 client/core/protocol 三个 crate 指向所选 DBProxy worktree。Linux 使用原独立验收 volume，DBProxy 干净源码归档 SHA256 为 `f0b26cd30c113f0cbc6faeea4076be38c712dae7b33cbc2bb844cca59947a982`，解至该 volume 的忽略目录；不引用用户数据库或日常服务。

两边由 Cargo 自己解析和生成私有锁，逐包检查版本、`source = null` 与实际 manifest 路径；确认相对主锁仅去掉上述三个已发布 Git 来源行，其余字节保持。主锁 SHA256 `c7d8d2ef570254890cd8b230824aebc1d3930f0adb14babd78f57416f14bd34c`；候选私有锁 `16ce66c67476afa65b88b47c6997971c55b89e5256e23aff475c1278bd1c0f6a`。这些覆盖与锁都不进入正式仓库。

Linux 同时使用已经核对的 Developer Tools Core 0.15.2、DBProxy TS SDK 0.6.2、Native Core 0.17.0 三个 npm 候选，139 个实际安装文件与两个 ESM 入口再检查通过。完整矩阵使用实际 V8、`io-uring,kcp`；保持无网络、无端口映射和独立容器。初始记录在 `temp/v0.7-sdk-joint-current-inputs.json`、`temp/v0.7-sdk-joint-current-metadata.json` 及 Linux volume 的 `temp/v0.7-sdk-joint-linux-inputs.json`。

## 离线 metadata 夹具失败

首次 Linux 准备阶段执行未指定目标平台的 `cargo metadata --offline`，在查询依赖图时尝试读取缓存中没有的 `bumpalo 3.20.3`，因此 exit 1；完整矩阵尚未启动。不能据此认定当前 Linux SDK 编译失败，也不能把后续测试写成这次运行通过。原外层日志 `temp/v0.7-sdk-joint-linux-run.log`，原 metadata 日志在 volume 的 `temp/v0.7-sdk-joint-linux-metadata-initial.log`。

正确做法是将身份查询限定到实际目标 `--filter-platform x86_64-unknown-linux-gnu`，继续保留 offline；恢复前核对已生成的 patch 和私有锁，不重复初始化、覆盖源码或手工改锁。修正后的实际 metadata 已通过，随后矩阵的 Linux Clippy 也成功编译这三个候选 crate。不能删除依赖、替换 crate 版本、启用 `DOCS_RS` 或跳过真实 V8 来处理缓存问题。

## Windows 结果

`node temp/v0.7-run-sdk-joint-windows.mjs` 通过，实际运行 `node tools/run_cargo.mjs clippy --all-targets --features kcp --locked --offline -- -D warnings` 和 `test --lib --bin TiangZ --features kcp --locked --offline`。Clippy 完成于 25.07s，测试编译 38.93s，**20 + 222 = 242** 项 Rust 测试全部通过，包括裸 V8 下的 DBProxy TCP 超时/资源释放；不是 PostgreSQL/Redis 存储恢复测试。

每步由现有测试运行器持有子进程树、设置 30 分钟期限并取得 exit 0，没有截断或回收失败；证据为 `temp/v0.7-sdk-joint-current-windows.log`、`temp/v0.7-sdk-joint-current-results.json`。验收前后主 Cargo.lock 与普通 Host 完全相同，Host SHA256 仍为 `1400787a90e7ac85516560ddfa7267e241603b6a6889c308200810765a3797ef`。本批 Windows 为 Rust/Clippy 联验，没有重跑 TS 完整矩阵或更新主 Host 为候选 SDK。

## Linux 结果与边界

首轮 `npm run verify` 已取得 exit 1：**check 8/8、quick 33/33、full 8/9**，full 587147ms，Rust **268** 项及 Clippy 通过。短测 524 请求/响应且无 RPC 错误、重复或版本混对，故障矩阵检查 2284 响应、三个宿主 exit 0/未强制退出；两个 Native 模块编译日志明确解析当前三个 SDK crate，实际 V8 运行通过。只有最后新建 Rust 脚手架失败。

该失败是离线缓存缺少 `refs/remotes/origin/tags/v0.6.2`：原缓存只有 `refs/commit/e9963d2…`，带发布来源的旧锁可以定位该 commit，但从临时 path 锁创建的全新组合工程还需解析 manifest 中的 tag。不能将旧模块命中缓存当作新建工程可构建，也不能改 manifest/tag 或手工写锁。先核对本机 Windows Cargo 已缓存 annotated tag 的 peeled commit 为 `e9963d2e08fd64bd5c3dca04e434705a6222af83`，再以本地 `git fetch --no-tags` 将这一真实引用导入专用 Linux Cargo 缓存，导入后再次核对相同 commit；没有访问远程或伪造 tag，日志 `temp/v0.7-sdk-joint-linux-cache-ref.log`。

随后仅复测失败项，保持 network none、offline 和相同源码/SDK/主 Host：`node tools/module_native_scaffold_self_test.mjs --runtime` 在**全新** `rust-scaffold-YUgIkJ` 上通过，85.034s，含 Rust 构建、实际 RPC、正常停机和旧二进制拒绝。由现有运行器设置期限并持有所属进程，exit 0、无输出截断/回收失败；普通 Host 与私有 Cargo.lock 在前后保持相同。没有重跑已通过的八项，不能把原 full 8/9 改写成单轮 9/9。

实际候选 Host 与两份热更报告共同 SHA256 为 `d71e2b64425bfbb3edfcd82e3350ea6c4351d2243be1b2ff0399694da526b1eb`，区别于上一批发布 SDK Host。原始完整日志、JSON/XML、失败、安装/源码身份与独立复测已保存至 `temp/v0.7-sdk-joint-linux-evidence/`；外层日志为 `temp/v0.7-sdk-joint-linux-run-retry.log` 和 `temp/v0.7-sdk-joint-linux-scaffold-retry.log`。本批所选项目至此分别取得通过证据，前一批 Native 0.17 的发布 Rust SDK 结果仍单独保留。

DBProxy 自身的真实 PostgreSQL/Redis 恢复、只读容量观测和未覆盖范围见其 `docs/v0.7-recovery-acceptance.md` 与本工程[实施进度](v0.7-progress.md)。本批不新增存储故障、长稳或远程发布。正式依赖仍应在所选 SDK 发布可引用 tag 后更新，再做发行冻结验证。
