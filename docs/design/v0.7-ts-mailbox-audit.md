# 0.7 TS mailbox 所有权盘点

后续[Host backing store 观测](v0.7-host-backing-store.md)已将原 Process 账本随 Box 安全转交 V8，最后所有者释放才减整块字节。真实 API 的小视图/Native 共享引用、Process 80×1 MiB 的正常与停机保留/回收分别通过；Windows 含 KCP **8/33/9**、Rust 263 项、Linux 实际 267 项通过。真实控制 RPC 排空后仍有 129414 字节被记录，不能把控制确认/请求完成或单批上限替代真实存储寿命，也不能以该非零直接判断泄漏。字节硬额度尚未冻结，需先保证已执行业务 completion 的准入与进展，不能直接套数量聚合确认。

后续[控制入站](v0.7-control-ingress.md)已完成跨 Native/V8/TS 的 65536 项未开始总量限制，实际开始/销毁确认、满额完成旁路和断线等待均验证。相关 TS 43/43，Windows 含 KCP 完整 **8/33/9**、Rust 262 项、Linux 实际原生 266 项通过；真实默认额度峰值 65536 后归零，原连接恢复。下方隔离 TS 直接注入仍是原反例，绕过 Native 的探针不受生产准入保护；当前剩余重点为实际存活 backing buffer/解码后持有及 Linux 完整游戏矩阵，不能将任务数量结果外推为字节上限。

后续 backing store 审查已核对锁定源码：deno_core 0.411.0 的 `convert.rs` 中 Uint8Array 先把 Vec 转成 Box slice，再以 `new_backing_store_from_bytes` / `with_backing_store` 转交 V8；这里不能假定另有一次 payload 拷贝。业务帧复制进 Host packed Vec 才是此前确定的复制边界。v8 150.4.0 的自定义 backing store 容器入口在 sandbox feature 下不可用；当前 `node tools/run_cargo.mjs tree -i v8 -e features --features kcp --locked --offline` 结果记录于 `temp/v0.7-host-backing-v8-features.log`，未启用该 feature。下一步先验证可带 Rust 所有者的真实 V8 backing store/子视图寿命；GC、完成通道的释放进展、混合批次计费和原生响应暂存须独立设计，尚未冻结新预算或宣称已覆盖 TS 驻留字节。

控制入站的隔离 Node 探针已执行：一个 ordered 断线钩子未结束时，520 × 128 条后续 Disconnect 在 TS 保留 **66560** 条，放行后 130 轮排空，钩子总计 66561 次。证据 `temp/v0.7-control-ingress-audit.json`、命令 `node temp/v0.7-control-ingress-probe.mjs`；没有物理 Socket 或 Session。后续[控制入站设计](v0.7-control-ingress.md)限定 Native→V8→TS 的未开始控制数量；它不为纯 TS 直接注入伪造 Native 准入，也不解决 Actor DTO 所持 backing buffer 的字节计费。

后续[Native 批次元数据](v0.7-native-scene-batches.md)已将跨批次保留槽限制为共享 65536，复制/分配前整批准入，整批容器真实销毁才归还。Host 28/28、最终调度 8/8、含 KCP 完整 **8/33/9** 通过，真实最大批次峰值与排空、258 项批次部分完成后的保留均验证。该保守槽位计费不等于全 Process 网络并发或全部 Native/TS 内存，控制通知与已知 backing buffer 所有权仍需单独处理。

后续[期限句柄](v0.7-deadline-handles.md)进一步消除高频本地/停机期限对 Deno u32 通用编号的消耗；实际 V8 的原 131079 次创建/释放后通用编号不再前进，原生 9/9、相关 43/43、含 KCP 完整 **8/33/9** 通过。专属表保留不复用安全整数、独立停机空间与最后引用归还。Native 每批 256 执行槽仍不等于跨批次元数据总量上限；原生传输、控制通知和 TS 驻留字节继续分开审查。

后续[远程排队期限](v0.7-remote-operation-deadlines.md)已统一单调绝对时间，原生未开始项独立到期，sleep 不占网络执行槽。相关 43/43、原生专项 4/4、含 KCP 完整 **8/33/9** 通过；真实 256 个长 RPC 占槽时 call/send 各在 Rust 队列记一次过期，单向送达 0，恢复成功。下方 20ms/77.32ms 探针和原 256 槽问题保留为修复前事实；控制通知背压、原生跨批次总量、TS 存活 backing buffer 和全部业务堆仍不是这项期限的保证范围。

后续[停机期限](v0.7-shutdown-deadline.md)已使用独立一项 Native 预留与共享 stop 结果，创建失败仍执行清理，相关 35/35、含 KCP 完整 8/33/9 通过。普通远程期限仍有独立证据：`node temp/v0.7-remote-deadline-probe.mjs` 将 20ms 的 call/send/sleep 在 TS 队列暂留 **77.32ms**，flush 仍打包原 20ms；结果 `temp/v0.7-remote-deadline-audit.json` 仅记录实际 TS 数据，不发网络。与下方原生 256 槽延后轮询一起，需要统一单调绝对期限、未开始项的过期处理和有背压的完成通知契约；只在被轮询时检查期限不足以保证未开始项及时完成，也不能宣称严格实时响应或已取消对端业务。

后续[远程 Host 共享准入](v0.7-host-operation-admission.md)已补齐 call/send/sleep 的联合条数与打包字节、输入帧和 flush 失效隔离，相关 27/27、含 KCP 完整 8/33/9、真实 65536 消息及 64 MiB 满批恢复通过。下方“尚未修改远程准入”描述的是原始探针时点。原生批次只同时执行 256 项，后续项仍在首次轮询时取得新的相对超时；仅在首次轮询检查过期还不能保证排队期间及时返回，需要独立调度/期限契约。停机 watchdog 仍使用普通 sleep 操作，其专用资源也另行处理，不能把本批成本上限当作时间或整个内存的上限。

2026-09-26 原始代码审查记录。后续[mailbox 生命周期](v0.7-mailbox-lifetime.md)已处理出队引用、空闲池、销毁终结及本地调用热更计数；以下对旧路径的发现保留。两级任务/字节准入、超限行为和控制通知预留仍需独立实现，本记录不代表 TS 驻留内存已经有界。

后续 [Actor 两级准入](v0.7-actor-mailbox-capacity.md)独立处理每 Actor/Process 任务总量与单向拒绝传播，[Spawn 总量](v0.7-scene-task-capacity.md)处理已接受的后台任务，[本地 Scene 准入](v0.7-local-scene-capacity.md)补齐 4096/EntryScene、16384/Process 的本地 call/send 实际节点所有权，并验证满额时 Host completion 在热更暂停期间仍能排空。原始发现中 Actor/本地 Scene 无数量上限和单向吞过载不再描述当前候选；网络控制通知预留、已知二进制保留和期限资源仍分别待完成，不能据此宣称全部 TS 内存有界。

后续[本地调用期限](v0.7-host-deadlines.md)已处理提前完成后遗留的计时资源，并区分原生期限与业务取消。独立 Node 边界探针 `node temp/v0.7-host-operation-admission-probe.mjs` 又发现原远程队列的混合准入缺口：先接受 65536 个单向消息，再接受一个 RPC，提交了 **65537** 项、1245207 字节，记录 `temp/v0.7-host-operation-admission-audit.json`。该探针仅记录打包，不发网络；Rust `decode_packed_scene_operations` 明确拒绝大于 65536 的整批，因此各入口各自限额不足以保证共享批次有效。下一批应在接受新项之前统一验证共享数量与打包成本/帧合法性，避免后来一项使此前接受的整批失效；当前尚未修改远程准入，不能把本地期限验收当作该路径已修复。

`EntryScene` 的网络入站分 control/data 两队列。Rust 看到 pendingIngress 会暂停普通数据注入，但继续每轮最多 128 条控制事件；因此“每轮有界”不能证明 TS 控制积压总量有界。unordered 网络任务已有 4096 并发上限；本地 Scene dispatch 与 Actor mailbox 的待执行队列仍无共享深度/字节总额。断线事件必须保持业务顺序并释放 Session，不能把它当普通丢弃消息。

`ProcessHost.runActorMailboxVoid` 和 `EntryScene.dispatchMailboxVoid` 在 busy 时只入队并返回 undefined，不返回真实完成 Promise。资源额度若包在调用者返回值的 finally 上，会在任务尚未执行时提前归还。正确释放点必须落在队列节点实际同步结束/异步完成或销毁时取消未执行节点的位置。正在运行的业务 Promise 不能因等待超时或 owner 销毁被假定已经结束；ordered 串行和热更排空条件必须保持。

两处队列的空闲节点池目前会保留历史最高数量；退队数组在压缩阈值前仍引用旧槽。限额与销毁修改必须同时核对节点、闭包、帧切片的最后引用，不能只减少统计计数。Actor 已有销毁时拒绝待执行 RPC 的路径，EntryScene 销毁目前主要处理 latest 转发与实体销毁，需补齐队列终结的对应验证。

帧视图可能持有整个 Host packed ArrayBuffer；仅统计 frame.byteLength 会低估其底层存储。反过来，为每个切片累计整个 backing buffer 是保守准入成本，必须明确不能称为精确内存。Actor Handler 进入队列前已解码为业务对象，任意闭包也可捕获对象图；编码大小不能冒充这些对象实际堆占用。后续至少分别定义任务数、已知二进制保留成本与无法测量的业务对象边界。

过载不能只抛异常：ProtocolRegistry 当前会将单向 Handler 异常记为 HandlerFailed 并返回 undefined，ProcessRuntime 的本地 send 也记录后返回。因此新增拒绝需穿透到本地准入调用或明确关闭其网络来源，不能丢掉未接收的事实消息后继续报发送成功。RPC 应保留 SceneOverloaded 和原关联号；过载响应本身亦不能建无界队列。

Rust `packed_events` 是另一份拷贝：逐帧复制后原 ingress 守卫可释放，生产者可在同批尚未交给 V8 时补入新帧。现有 ingress 字节额度不能替代 Host 批次额度。后续[Host 批次验收](v0.7-host-event-batches.md)已独立完成含头部 64 MiB 单批上限与运行/停机真实 V8 测试；TS 视图寿命和总量仍需分别验证，不能把单批额度当作全部存活副本上限。

后续小额度反例须覆盖跨 Scene/Actor 的共享竞争、本地 RPC/单向投递、ordered 跨 await、unordered 在途、销毁拒绝与迟到完成、断线通路、节点池高水位、同 backing buffer 多视图及真实 Rust→V8 入口。基线负载和现有 500 请求故障矩阵通过后，才能冻结默认值及部署迁移说明。

后续审查：`ProtoReader` 的 bytes 字段仍以 `subarray` 返回收到的原存储；Session/Unit 单向绑定在解码后调用 `runActorMailboxVoid`，busy 时 Scene 可先返回，而排队闭包中的 DTO 仍保留 bytes 视图。因此仅在 EntryScene 的 ingress Promise finally 归还“二进制额度”会漏掉已转入 Actor 的保留量。需要给实际后继工作转移/增加保留所有权，或者明确复制/计费策略，不能仅按第一层调用返回归还。任意业务闭包/Component 继续持有对象的堆内存依旧不能由编码长度精确代表。TS 任务数量准入、已知 runtime 二进制保留成本和业务对象内存须分别报告。
