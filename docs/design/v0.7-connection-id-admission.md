# 0.7 连接编号在分配入口遵守协议宽度

本批基于 `d829fdd`。TCP/Auto/WebSocket、io-uring 和 KCP 从 Process 共享 `AtomicU64` 直接 fetch_add 取得连接编号；Rust→V8 的固定 Host 事件头、TS 关闭连接桥则只接受 uint32。`HostEventBatch::try_push` 会拒绝超宽编号，但那时连接可能已经登记或处理了输入。这里需要补齐分配时的边界，不修改线上帧格式。

## 冻结的行为

保留从 1 开始、整个 Process 生命周期内不复用的连接编号；最大值为 `u32::MAX`，最后一个合法编号正常使用。多个 listener 使用同一原子分配入口，边界竞争不重复、不回绕，也不生成零。计数器达到上限后的下一次分配明确失败，保持计数器不变，不开始握手、建立 writer/Session 或向 TS 发布非法编号；已经取得的连接/握手名额随失败归还。

编号耗尽是无法在当前编号空间内恢复的 endpoint 错误，交给既有 Process 监督与有期限的停机路径，不继续宣称 listener 健康。错误明确指出连接编号耗尽及需要重启；不通过重置计数器复用仍可能被旧消息引用的身份，也不临时放宽 Native/TS uint32 检查。此改变把失败提前到发布前，不宣称提升了可用编号数量或自动故障转移能力。

KCP 的线上 local_conn 分配仍是独立机制，不将其截断/避碰结果当成 Host connection_id 已合法。只统一各 backend 的 Process 编号分配，不调整容量、握手、KCP 缓存、字节预算、业务超时或业务 ID。

## 验证与交付

先用生产 endpoint 与真实 TCP：从最后合法编号开始，第一条连接的帧正常进入 Host 事件头；下一次连接不能发布超宽事件，endpoint 明确失败，writer、连接/握手名额和 Socket 回收。有限边界种子不是实际执行 2^32 次连接或生产事故复现。原子分配单测覆盖最后两项的并发竞争、非法零/已耗尽/u64 极值输入与计数器不回绕；真实 WebSocket/KCP 路径与 io-uring 条件编译分别验收。

Rust/Host 边界需要重建重启，执行含 KCP 完整矩阵、Linux 条件编译与 AI 实际归档。实现留在现有 admission 模块，各 backend 调用同一函数；不新建只转发的层。没有新配置、Native schema、Stable TS API 或协议字段，两个 VS Code 插件无需改版，AI 同步不复用与协议宽度规则，继续保持独立版本。
