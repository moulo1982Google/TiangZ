# 0.7 Linux 原生运行验收

本批从 `8ec6fa8` 的 Windows 完整矩阵通过状态开始。之前多次 `DOCS_RS=1 cargo check --all-targets --features io-uring,kcp --locked` 只证明条件编译；当前 endpoint 测试默认创建 epoll backend，即使编译了 io-uring feature，也不能据此声称运行了 io-uring。

## 本批范围

先在专用 Linux 容器确认 Rust/Node、实际内核与 io_uring_setup 能力，再去掉 DOCS_RS，真正链接 V8 并运行现有原生用例。复用当前锁定 Cargo 依赖，单独保存 Linux 目标产物，不覆盖 Windows 宿主或任何用户容器。容器只绑定本候选源码（只读）与本任务缓存，不映射宿主端口、不接入用户数据库；安装工具仅发生在专用镜像。

默认容器安全策略和内核能力必须区分。若默认策略拒绝 io_uring_setup，先保存实际错误，再仅对本次隔离容器调整 syscall 策略复测；不修改宿主内核参数，不使用 privileged，不将失败变成静默跳过。成功创建 ring 只证明能力，不能代替实际传输验收。

若环境允许，复用生产 EndpointContext/IoBackend 和已有 Socket 夹具增加 Linux io-uring 专项：真实收发、入口 audience、连接/握手共享名额、部分握手停止、writer 排空/取消以及最后合法连接编号。实际 I/O 后确认 writer、名额和端口释放；测试进程与 Tokio 仍存活时验证，不能靠整个容器退出代替资源回收。Linux 专项采用明确的平台/feature 条件，不更改默认后端、协议范围或失败策略。

先跑未改代码的 Linux 基线，再根据实际反例决定是否需要生产修复。每个失败分别记录环境、测试夹具或框架原因，禁止扩大超时、改为 epoll、跳过 V8 链接来假装通过。若发生框架修改，更新双方 AI 入口并重跑相应 Windows 完整矩阵；只增加平台测试时运行必要的平台检查，不无故重复已通过的昂贵业务矩阵。

本批不是 Linux 多发行版认证、长期压测、生产容器发布或完整图形客户端验收。Developer/Native VS Code 与 AI 包没有因平台验证自动升级版本的理由；只有实际契约改变时才同步对应维护源和分发。

## io-uring 真实反例与关闭所有权

实际 RED 已确认：`temp/v0.7-linux-uring-handshake-red.log` **1 failed**，6.05 秒，编译 1m09s。生产 io-uring endpoint 收到部分前导 `G`，5 秒后连接/握手名额已经归零、writer 表为空，但客户端等到外层 6 秒仍没有 EOF/reset；失败发生时 listener 与测试 Tokio 都仍存活。这是实际 Socket 没有关闭的框架缺陷，与前面默认容器的 EPERM 无关。

最小修复在原 io-uring 模块加入一个 Socket 关闭守卫：握手期间持有，验证成功后将同一个所有者交给 writer；握手超时/拒绝、writer 出错/超时/取消均同步 shutdown，唤醒保留 FD 的内核操作。正常路径仍先排完已接受写队列才释放守卫，不在 reader 开始关闭时提前截断最后通知。守卫不能留在等待 Disconnect 入队的 reader 中，否则控制通道堵塞可能再次延长 Socket 生命周期。

不改连接/握手数值、5 秒握手期限、原写入/停止期限、默认 backend 或线上协议；不以提升外层测试超时、提前删统计或关闭 listener 来掩盖缺陷。复测同一真实用例，另补实际 io-uring audience、最后合法编号与正常写队列排空，再跑 Linux 全目标与 Windows 回归。此修复须重建并重启 Process。

首个关闭守卫版本的完整用例仍失败，`temp/v0.7-linux-uring-handshake-green.log` **1 failed**、6.06 秒：已通过旧 Socket 关闭检查，但新连接不能进入 writer 登记。原 listener 每次 `select!` 收割连接任务时会丢弃尚未完成的 accept；原 accept 留在内核，新连接可被无人消费的成功结果接走。现在整个监听循环保留同一个 pending accept，只有实际收到结果才重置；停止时 shutdown listener，并在原一次 stop 总预算内消费原 accept 结果和排空连接，成功接入的竞态结果也正常关闭。

为安全控制监听 Socket，Linux 的 io-uring feature 显式使用已有锁中的 **socket2 0.6.5**（MIT/Apache-2.0），避免手写 libc FFI 或伪造流类型。没有升级现有传递包；通过 Cargo 正规解析更新直接依赖关系，再检查锁差异。符合[依赖策略](../security/dependency-policy.md)允许开发期同步解析的规则，DBProxy tag 保持已发布 v0.6.2；此依赖变化属于本次后端修复，不混入上一批已完成的编号提交。

依赖解析日志 `temp/v0.7-linux-native-dependency-resolution.log`，Cargo.lock 实际只有 TiangZ 的依赖列表增加 `socket2 0.6.5` 一行。首个保留 accept 版本在编译期触发 E0505：借用 listener 的 Future 与 listener 本身不能一起被移入同一 async 关闭块，`temp/v0.7-linux-uring-handshake-final.log`。改为先 shutdown，消费原 accept 并排空连接后在外层 drop listener；保留借用检查，没有 unsafe 绕过。这是实现阶段编译错误，不是额外的运行时反例。

## 可复现入口

工具镜像定义保存在 [Linux Native Dockerfile](../../tools/docker/linux-native/Dockerfile)，在初次镜像基础上补齐同版 Clippy/rustfmt 后正式重建。只负责 Rust/V8 原生验证所需工具；它不安装全套 .NET/Luban/GUI，也不等于完整 Linux TS 模块构建环境。

在候选仓库根目录构建该镜像，将源码只读绑定到 `/work`，独立 Cargo/target 缓存分别绑定 `/cargo-cache`、`/target`，设置 `CARGO_HOME=/cargo-cache`、`CARGO_TARGET_DIR=/target`、`RUSTUP_TOOLCHAIN=1.97.1-x86_64-unknown-linux-gnu`。首次允许下载已锁定依赖，后续可 `--network none` 加 `--offline`。实际 io-uring 容器必须具备已确认的 syscall 权限，本机专项使用前述仅限测试容器的策略。

```text
docker build --pull=false -t tiangz-v07-native-validation:20260926 -f tools/docker/linux-native/Dockerfile tools/docker/linux-native
node tools/run_cargo.mjs test --all-targets --features io-uring,kcp --locked
node tools/run_cargo.mjs test --bin TiangZ --features io-uring,kcp --locked io_uring_ -- --nocapture
node tools/run_cargo.mjs clippy --all-targets --features io-uring,kcp --locked -- -D warnings
```

后三条在专用 Linux 容器内运行，不设 DOCS_RS；每次 Cargo 进程总保护期限 1800 秒，用例自身 Socket 期限仍保持原值。容器必须以本任务专名、label、`--rm --init` 运行并保存实际退出码；不能只看日志尾部的某一条 passed。Windows 仍用正规 `TIANGZ_VERIFY_CARGO_FEATURES=kcp npm run verify`。
