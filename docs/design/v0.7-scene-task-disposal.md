# 0.7 动态 Scene 后台任务销毁契约

2026-09-26 实施前冻结。本项延续 [mailbox 生命周期](v0.7-mailbox-lifetime.md)，修复 `Scene.Tasks.Spawn` 的所有权，不新增业务任务 API、配置、后台线程或取消 Promise 的承诺。

## 已证明的问题

`temp/v0.7-scene-task-disposal-first.log` 的两个真实 Runtime 单测均失败。第一项等待任务主体已经进入，再销毁动态 Scene：Scope 正确保留任务，但 ProcessHost 仅遍历仍可路由的 Scene，导致 pendingAsync/热更排空漏计。第二项停止旧 Runtime 并在同一 JS realm 启动新 Runtime，旧任务完成后的 finally 通过 `TimerSystem.Instance` 取消 watchdog，实际调用了新 Runtime 的 Timer 服务。计时器 ID 可能复用，句柄必须同时绑定原服务实例。

## 修复边界

Scene 销毁立即请求协作取消并停止告警 Timer；尚未开始的任务不再执行主体，已经开始的任务直到真实 Promise 结束才释放。ProcessHost 从路由移除 Scene 后，单独持有仍在途的 Scope；最后一个任务完成时主动通知 Host 移除引用，不依赖下一次指标读取、下一帧、GC 或弱引用。相同 SceneId 的新实例与旧 Scope 分别计数，注销路由不等于排空。

watchdog 保留创建它的 TimerSystem 实例，取消只使用该实例，先清空自己的句柄和所有者引用。已销毁 Scope 不重新安排告警；迟到完成不能访问新 Runtime 的 Timer 单例。停止 Runtime 仍不强行终止 JavaScript Promise，也不回滚已发生的副作用。业务需响应 `signal.aborted`，不能把析构当作可靠领域任务的完成确认。

此项只补生命周期计数。每个 Scope 的 256 个任务上限保持，多个活跃或已销毁 Scene 的进程总额度仍属于 [TS 预算后续](v0.7-ts-mailbox-audit.md)；不能宣称进程任务数、TS 堆或物理 I/O 已有界。

## 验证与迁移

保留首次失败，使用可控结果 Promise 验证启动前取消、执行中取消、正常/失败完成、同 ID 新旧实例共存及真实所有者引用释放。重启用例同时检查新 Timer 实际仍可取消，而不只监视函数调用。真实 Rust/V8 夹具在网络启动请求已经完成、动态 Scene 已销毁后申请热更，必须因仍在途任务而拒绝且 generation 不变；释放真实任务后恢复。按生命周期规则执行完整 `npm run verify`，记录实际 Host 和热更报告身份。

本次 Core 源码变化需要完整构建和 Process 重启，不通过 Hotfix 替换 Model。不新增协议字段；隔离验证继续使用正式生成的夹具协议与已有控制模式字段。
