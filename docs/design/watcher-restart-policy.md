# Watcher 持续重启策略（0.7.2）

需求方 2026-10-09 提出，同日确认方案。

## 背景

苟道三国的部署机器内存不稳定，进程会偶发崩溃。需求方的要求：

- 崩溃后必须能自动恢复，影响只限于崩溃的那个进程。
- Gate 崩溃：让这个 Gate 上的玩家等它重启，或换一个 Gate 后重新登录。
- Host 崩溃：让玩家稍后重新登录。
- 进程启动只要几秒，不需要更复杂的恢复手段。

现有的 `process.lifecycle.restart` 是**有界重启**：

```json
"restart": { "maxAttempts": 3, "windowMs": 60000, "backoffMs": 1000 }
```

规则是：时间窗内次数没用完，就固定退避后重启；用完以后，Watcher 回到“整组失败收束”。

整组失败收束的后果：
1. Watcher 通知全部子进程停机，然后以非零状态退出。
2. 容器重启策略（苟道三国部署用 `unless-stopped`）把整个区服容器重新拉起。
3. 结果是**一个进程反复崩溃，整个区服的玩家都被断开**；只在内存里的数据（目前苟道三国的主公、领地）全部丢失。

对“偶发崩溃”的机器来说，这把局部故障放大成了全服故障。

## 目标

1. **只隔离出问题的进程**：一个进程反复崩溃，不影响同组其他进程。
2. **不轻易放弃**：偶发崩溃立即恢复；一启动就崩的（配置错误、代码缺陷），越重试越慢，避免刷屏和空转，修好后自动恢复。
3. **向后兼容**：不改配置的进程行为与 0.7.1 完全相同。
4. **能被发现**：持续崩溃要能报警。由进程侧指标和外部监控负责，Watcher 不新增网络出口。

## 方案

`restart` 新增 `policy`，可选 `bounded`（默认）和 `persistent`：

```json
"restart": {
  "policy": "persistent",
  "backoffScheduleMs": [1000, 5000, 30000, 120000],
  "stableAfterMs": 600000
}
```

| 字段 | 适用 | 默认 | 范围 | 含义 |
|---|---|---|---|---|
| `policy` | 全部 | `bounded` | `bounded` / `persistent` | 重启策略 |
| `maxAttempts` / `windowMs` / `backoffMs` | bounded | 3 / 60000 / 1000 | 不变 | 原有有界重启 |
| `backoffScheduleMs` | persistent | `[1000, 5000, 30000, 120000]` | 1–10 项，每项 1000–600000 ms，单调不减 | 第 n 次连续崩溃用第 n 项退避，超出后一直用最后一项 |
| `stableAfterMs` | persistent | 600000（10 分钟） | 10000–86400000 | 重启后连续运行这么久，连续崩溃计数清零 |

### persistent 的行为

1. **子进程退出或重启失败**：先看它上一次连续运行的时长。
   - 达到 `stableAfterMs`：连续崩溃计数清零。
   - 然后按计数取对应的退避时长，计数加 1，安排重启。
2. **永不因为这个子进程停止整组**。整组停机只来自运维信号，或者未配置重启（或 bounded 预算耗尽）的其他子进程退出。
3. 退避等待期间，Hotfix 和配置广播会跳过这个子进程（与现有行为一致）。重启后，Watcher 会重放本生命周期最近一次的候选（与现有行为一致）。
4. 运维停机时，如果子进程正处在退避等待中，不再启动它，直接计入已停止。
5. 每次崩溃写 error 日志，包含进程名、退出状态、第几次连续崩溃、下次重启前的等待时长。每次重启写 info 日志。

以默认表为例：
- 偶发崩溃：1 秒后恢复。
- 10 分钟内连续崩溃：等待依次为 5 秒、30 秒，之后每 2 分钟试一次。
- 修好或机器恢复后，最多 2 分钟内自动回来。

### bounded 保持不变

省略 `policy`，或写 `bounded`，行为与 0.7.1 完全相同，包括“预算耗尽后整组失败收束”。新字段对 bounded 没有影响。

### 适用范围

自动重启只恢复**进程**，不恢复**业务数据**。哪些进程适合用 persistent，由游戏按自己的恢复契约决定：

| 适合 | 不适合 |
|---|---|
| 状态可丢、玩家重新登录即可恢复的进程（苟道三国：Gate、PlayerSceneHost、Login、战斗服） | 持有不可丢的唯一状态、又没有持久化的进程（苟道三国当前的 Directory：主公只在内存，重启等于清空区服，应继续整组收束） |

## 监控与报警

Watcher 不新增指标端口，持续崩溃由已有信号覆盖：

| 情形 | 信号 | 苟道三国报警 |
|---|---|---|
| 崩溃后已重启 | 进程 `tiangz_process_uptime_seconds` 回落 | 一般：“进程被重启” |
| 10 分钟内重启 ≥ 3 次 | `resets(uptime[10m]) >= 3` | 严重：“进程反复崩溃”（新增） |
| 处在长退避中（进程不在） | 健康端口 `up == 0` | 严重：“进程不可达”（30 秒） |

## 兼容性与验证

- **配置兼容**：新字段可选，旧配置不变。0.7.1 宿主遇到 `policy` 字段会按未知字段拒绝启动，因此游戏要和 0.7.2 宿主一起升级配置。
- **单元测试**：
  - 退避序列：1、5、30、120、120 秒。
  - 稳定运行达到 `stableAfterMs` 后计数清零。
  - bounded 预算与原行为一致。
  - 配置解析与范围校验。
- **苟道三国 220 实测**：
  - 连续 kill 同一 Host 4 次：同组其他进程不受影响；钉钉收到“进程反复崩溃”。
  - 停止注入后，进程自动恢复，玩家重新登录。
- **开发启动器**：苟道三国的 `land-demo.mjs` 读同一份配置，实现同样语义，保证开发、测试和正式行为一致。

## 不做的事

- 不做跨机器迁移，也不做“换一台机器启动”。
- 不新增 Watcher 指标端口，不让 Watcher 直接发通知。
- 不改变 bounded 语义，不改未配置重启的进程的整组收束语义。
