# 0.7 Host 入站打包批次

2026-09-26 实施前冻结。N1 本步只约束 Rust 向 V8 交付的单份 packed event buffer，不把已解码 ingress 额度当作另一份副本的额度。

## 契约

- 每批最多 67108864 字节（64 MiB），包括 4 字节事件数和每条 13 字节头。默认规模沿用现有 ingress/Host 出站的 64 MiB；本步为内部固定硬上限，不新增部署字段，不改变插件版本。现有 maxEventsPerUpdate 仍是另一项上限，先到者结束批次。
- 先核对下一事件完整成本，再分配/复制。放不下就结束当前批次并执行一次 Update，不在同一次 Update 前连续注入多个大批次。
- 控制/数据接收通道各最多保留一条尚未装入的原事件，下一次同通道取队优先取它，保持 FIFO；退回不消耗第二次准入，不改变连续控制事件的公平计数。暂存仍持有 Bytes ingress 守卫，队列深度直到交付/热更延后/停机丢弃才扣除。mpsc 已空出槽位，所以物理队列以外最多另持有两条事件，不能把配置的 mpsc 槽数称为所有事件对象的绝对上限。
- TS pendingIngress 时仍可取完成/断线控制通知；被暂存的数据帧不能阻挡它们。Hotfix 延后队列仍维持自己的既有上限，新批次边界不放行热更暂停中的业务帧。正常运行和停机 completion 排空共用同一编码与字节上限。
- 拆批是调度行为，不是业务拒绝：不丢弃或截断 payload，不产生伪造 SceneOverloaded，不改变 operationId/rpcId 或完成结果。已有 TCP/WS/KCP 与 Inner 响应帧上限为 1 MiB，合法单帧一定能进入空批。非法连接 ID、无法装入空批的异常内部事件等在复制前明确终止 Runtime，不将其伪装成业务准入拒绝或成功；诊断错误字符串也不得豁免字节上限。
- 分配增长请求封顶，禁止 Vec 几何扩容请求超过批次上限。指标记录实际逻辑字节高水位和拆批次数；不称为进程 RSS、分配器物理占用或 V8/TS 存活 ArrayBuffer 总量上限。旧缓冲扩容时新旧分配可短时共存；交给 V8 后的 GC/视图寿命属于后续 TS 所有权边界。

## 验收

1. 真实 Process 事件循环和 V8 bridge：普通运行及停机期间分别交付超过 64 MiB 的完成通知，单批不越界、内容/关联号/顺序不变、所有通知到达后正常停机。
2. 小批次反例验证精确边界、头部成本、满批不复制/不归还原 ingress 守卫、恢复后交付；异常事件失败不部分改变批次。
3. 控制/数据各自 FIFO、退回后的公平计数、pendingIngress 控制进展、Hotfix 延后帧及接收端销毁回收。
4. 指标固定标签；实际 Rust 重建后完整 check/quick/full，Linux 条件编译单独记录。旧可执行文件或纯编码测试不能冒充真实宿主路径。

本步不含 TS mailbox/所有 completion 的进程总量预算、长稳、发布或生产评分。
