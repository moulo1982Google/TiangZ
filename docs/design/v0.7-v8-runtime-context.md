锁定依赖源码明确说明：isolate 构造时记录当前 Tokio handle，后续 V8 延迟前台任务用该 runtime 的定时器。缺少 handle 时不能直接立即执行、静默丢弃或跨 C++ 展开 Rust panic，因此主动终止。原测试输出捕获隐藏了 abort 前诊断；core 中精确栈才确认本轮原因。此前 Windows 无栈异常仍不能认定同源。

生产 `run_process` 的预检、业务 V8 和独立热更预检已经在 `js_event_loop.enter()` 内创建；两个性能工具也是如此。遗漏发生在部分 `host` 同步测试、独立控制入站线程、backing store 探针和双 Native 模块临时 Rust 验收入口。`spawn_blocking` 保留 Tokio 上下文，现有异步 DBProxy 探针也已经在 Tokio 中。

## 本批最小契约

- `host::create_runtime` 在创建 isolate 前检查当前 Tokio handle，缺失返回明确 `Result::Err`，不创建后台 runtime、不设全局替代平台、不等待偶发 GC 才失败。
- 调用者拥有并驱动启用 timer 的 Tokio runtime，使它活到 V8 销毁之后。检查当前 handle 不能证明 timer 已启用或 runtime 将永远存活；生产入口仍承担这些条件。
- 漏配测试按各自原拓扑进入上下文：普通同步 V8 用例改为当前线程 Tokio 测试；手动驱动和独立线程用例在构造时 enter 已有 runtime；独立 backing store 探针持有自己的 current-thread runtime。
- 不改库版本/锁、V8 GC 参数、业务准入、测试并发、负载与原断言。`JsRuntime`、Model、Host 协议和插件版本没有新公共 API。
