## 故障时间表

60 分钟及以上阶段每小时一轮：第 2、12、22、32、42 分钟开始五类故障。30 分钟起点从第 2 分钟开始，每五分钟一个动作，完整覆盖五类故障。七级分别要求实际完成 5、5、10、20、40、80、120 个故障窗口。故障恢复期限与最终对账门槛不因短阶段而降低。

| 故障 | 注入与恢复 | 特别检查 |
| --- | --- | --- |
| 首选 DBProxy 节点退出 | 精确向节点 0 发送 SIGKILL，15 秒后启动相同字节和端口 | 保持负载客户端运行，保留各进程代次及退出原因 |
| 缓存丢失 | 强杀专用无 AOF/RDB 缓存 Redis，15 秒后启动 | 数据库权威读与事务继续遵守原契约，缓存修复不能产生死信 |
| PostgreSQL 崩溃 | 强杀专用 PostgreSQL，20 秒后启动并核对目标库真实查询 | 未确认事务沿用原操作号恢复，不能报告伪成功 |
| 存储网络断开 | 只断开本轮 DB 容器的专用 Docker 网络，15 秒后重接 | 本地 TCP 负载客户端继续运行，存储连接必须恢复 |
| AOF 积压恢复 | PG 停机形成已确认积压，冻结两个 DB 服务进程，强杀可靠 Redis 并启动 | 在任何服务进程恢复写入前直接比对积压证据，然后恢复服务与 PG |

最后一种故障先确认 PG 停机期间仍有成功的 AOF 入队，再冻结两个服务进程并等待已发出的操作稳定；负载客户端不暂停。用只读 Redis 脚本取得全部 40 个排队条目及 pending/processing/lease/sequence 语义状态，对二进制载荷编码并计算规范化 SHA256。Redis 重启后、服务进程恢复前必须逐项一致。不能只比较最终快照，也不能让重启后的新写入覆盖丢失项再宣称 AOF 恢复成功。此项验证容器内 Redis 进程崩溃，不等同整机断电、磁盘故障或备份恢复。

节点 1 在整个阶段不重启，只在上述 AOF 取证窗口被有界暂停；它承担完整时长的 RSS 趋势验证。节点 0 另按每个进程代次记录峰值及适用的趋势数据，不用反复重启掩盖另一节点的内存增长。

## 错误分类与通过条件

- Host 原有零 RPC 错误门槛不变。
- 数据库每五秒记录累计/增量计数，缺少连续观测、计数回退或调度中断都不能算通过。
- 可重试的读取、入队、事务和交易请求失败，只允许出现在与明确故障/恢复窗口重叠的观测区间。提交结果未知时，读取可能先于客户端收到原操作号重试结果，因此 `readsAheadOfLocalRevision` 也只允许在该窗口中增加。
- 缺失快照、低于已确认 revision 的读取、永久协议/事务错误、经济效果重复、账本不平衡、Outbox 对不上、死信，在故障期间也一律失败。
- 故障动作恢复后最多 180 秒内，必须观察到至少 60 秒无新增可用性错误/超前读取，且直接事务、交易、入队都重新产生成功进展。否则失败，不能无限扩大容错窗口。
- 各故障之间有正常负载窗口，最后至少保留三分钟无故障尾段。最终逐玩家读取、维护队列两次排空、正常停止和直接 SQL/Stream 对账仍全部必需。
- SQL 最终直接序号总和必须等于事务回执和客户端确认数；交易、钱包、账本、Outbox 的数量与零和关系保持原门槛；已发布事件 ID 集合必须与 Redis Stream 的唯一事件集合一致。

五秒计数区间是错误归属的采样精度，不冒充每个失败请求都有独立精确时间戳。原七个真实恢复契约仍单独保留，包括 COMMIT 已完成但回包丢失的精确注入用例；它们不能代替本次长稳时长。
