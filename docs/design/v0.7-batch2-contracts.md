## D2：Rust SDK 请求预算

- 保留 `ClientConfig.request_timeout` 字段、类型和默认 5 秒；改为一次逻辑调用的总墙钟预算，包含请求准备、许可/写锁等待、写入、等待响应、自动重连及重试。每个实际执行操作的 API 在首轮 poll 时创建预算，轻量转发入口由共同实现创建；Future 尚未 poll 时未接受执行。
- 同一操作的重试沿用一个本机单调期限，`connect_timeout` 仍约束连接阶段，外层剩余期限更短时由外层终止。初次显式 `connect` 的现有候选策略不在此改动中重做。维持最多一次自动请求重试，不新增重试层或退避默认值。
- 增加明确的 `RequestNotSentTimeout` 错误：整个逻辑操作从未进入帧写入阶段。只要任何一次尝试进入写入阶段，期限结束均保守返回现有 `RequestTimeout`（结果未知）；后续重试在队列超时不能把先前未知结果降为“未发送”。业务幂等号和 payload 始终沿用原值。
- 等待许可或写锁超时不注册/遗留响应关联，也不损坏连接。进入写入后失败或取消沿用关闭半帧流的 RAII；等待完整响应结束只释放当前关联，已有复用连接活性判断保留，其他在途响应仍可正常交付。迟到响应由唯一递增 rpc_id 丢弃。
- 使用同一绝对期限约束各阶段，并在拿到许可/锁后再次检查到期，避免一个已到期但立即 ready 的 Future 偷发请求。配置期限必须为正且可表示，不能让 0 意味着无限等待。
- 现有 `ClientRequestTiming.queue_wait/exchange` 和旧 observer 回调保持兼容，排队超时应完整归到 queue_wait；连接尝试继续使用既有观测入口。同步校验/编解码有协议大小限制，墙钟期限不抢占同步 CPU，但不得在校验或排队已经耗尽预算后发包。
- TS SDK 的 Transport 与 TiangZ Host 还需独立衔接；TS SDK 不能通过单独 `Promise.race` 假装撤销 Rust 队列。宿主当前引用已发布 DBProxy tag，联合候选验证要显式选择本地 worktree，不能提交临时路径依赖锁。

验收先保留反例，再检查许可占满、写锁占用、排队后响应、重连锁占用、慢候选握手、取消/部分写、正常并发、迟到响应和同操作重试身份。使用本机隔离 TCP/内存夹具，不执行真实数据库故障或长稳。

### Host 预算与取消

宿主从提交任务前开始使用既有 `persistence.dbProxy.requestTimeoutMs` 总预算，包含任务排队、连接池等待/建立和 SDK 操作。独立 Host 任务由调用方 RAII 持有，调用方取消后请求 abort；后台任务自身也持有同一截止时间，V8 忙碌不会令网络任务继续无期限运行。取得连接池后再次检查期限。

删除 Host 的整池失效/再次重放层，由 Rust SDK 独立连接恢复并保留操作身份；Host 的操作闭包为 `FnOnce`。宿主外层超时保守使用既有结果未知错误，暂不推断 SDK 内部是否已经发送。TS Repository 的显式 StorageUnavailable 退避重试仍需共享更外层预算，尚未修改，也不能把这一阶段当作全部 D2 完成。

当前 4 个 Host 所有权/期限测试通过，证据 `temp/v0.7-host-budget-msvc.log`。手动命令第一次只匹配 `gcc`，遗漏完整路径的 `CC/CXX` 而再次触发 LNK1143，日志为 `temp/v0.7-host-budget.log`；随后按编译器 basename 过滤当前子进程变量并重新构建。没有修改整机变量或第三方源码。

### N2 慢写配置冻结

新增 `process.network.writeTimeoutMs`：正整数 1..300000，默认 10000ms。默认量级沿用当前 Process 停机宽限 10 秒，但字段独立；它是可调整的初始保护值，不是容量/移动网络基准结论。一次出站批次从成功准入起，到完整交给 TCP/WebSocket 写出完成共用该期限，排队时间不能忽略；KCP 的该期限仅约束进入可靠传输前的宿主排队，不代替 ACK/重传预算。读对端长期停顿会比 0.6.2 更早断开，慢链路部署须显式配置并验证。

开始正常关闭后，全部已入队批次还共享既有 `stopTimeoutMs` 排空期限（与各批次剩余时间取先到者）；不能每批重新获得完整关闭预算。过期即关闭字节流，日志保留未完成的帧数/字节信息，资源守卫在所有路径回收。0 不代表无限，超过范围启动失败。Rust 反序列化/校验、TS 配置类型、VS Code Schema/说明与测试同步修改；这是 0.7 候选字段，旧宿主会拒绝它。

出站记账同步约束：排队及正在写出的批次必须持续占用现有帧数/字节预算；成功、发送失败、接收队列销毁、writer abort 都通过批次资源守卫恰好释放一次，不能靠每个 backend 的手写减计数维护。KCP 转发单帧持有原批次守卫直到最后一帧完成转交，允许保守占用，不能转发后提前释放。保持已有每连接数值和 KCP 共享队列的帧单位；KCP 内部重传缓冲及 Process 总量仍需单独度量与限制。

### Listener 生命周期实施契约

慢写首轮实现已验证：Windows 全目标含 KCP 共 179 条通过，Clippy `-D warnings` 通过；默认 TCP 入口真实慢读验证先收到帧头，随后停止读取并填满窗口/发送缓存，在写预算内回收登记和队列。另有确定性 duplex 验证生产 vectored writer 的 64 字节部分写，排队已过期不启动 ready I/O、总关闭预算和 writer panic 唤醒 reader。日志 `temp/v0.7-write-budget-green.log`、`v0.7-write-budget-clippy.log`。首轮 148/150 的两项 KCP 失败来自 TCP 端口选择不能保证 UDP 可用，夹具改为按协议申请。Linux 新代码 `DOCS_RS=1 cargo check --all-targets --features io-uring,kcp --locked` 再次通过（`temp/v0.7-linux-write-check.log`），仍不含 V8 链接/内核运行。

`Process -> EndpointTask -> 连接任务 -> writer` 建立实际所有权：任务句柄丢弃会请求取消，取消时移除 writer 登记并释放 Socket。正常停机先停止接受新连接/取消未完成握手，已有连接收到关闭信号后保留排空最后通知的语义。全部端点共享现有 `process.lifecycle.stopTimeoutMs` 排空预算（默认 10000ms），到期取消并回收其异步任务，不按连接数量累加超时；不新增配置默认值。外部进程监督仍负责无法协作的 CPU/V8 卡死硬截止。

Process 必须监视端点结果；非预期正常结束、accept 错误和任务 panic 都退出 ready 状态，并经过正常 Process 停机路径，最终返回失败，不能只记录日志继续报健康。某个端点绑定失败要撤销此前已启动的端点。io_uring 线程也接收停止通知并上交实际线程结束结果；KCP 收回 Session 登记和转发任务。健康端口的所有者丢弃也必须关闭其 listener，避免后续启动失败遗留。

验收包括真实 listener 丢弃、部分握手取消、活动 TCP/WebSocket 停机、端口重绑、启动中途失败回滚，以及可控端点错误/卡住任务。Linux 实验后端的编译与运行证据单独列出，不使用 Windows 结果替代。
