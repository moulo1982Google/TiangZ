## D2：Rust SDK 请求预算

- 保留 `ClientConfig.request_timeout` 字段、类型和默认 5 秒；改为一次逻辑调用的总墙钟预算，包含请求准备、许可/写锁等待、写入、等待响应、自动重连及重试。每个实际执行操作的 API 在首轮 poll 时创建预算，轻量转发入口由共同实现创建；Future 尚未 poll 时未接受执行。
- 同一操作的重试沿用一个本机单调期限，`connect_timeout` 仍约束连接阶段，外层剩余期限更短时由外层终止。初次显式 `connect` 的现有候选策略不在此改动中重做。维持最多一次自动请求重试，不新增重试层或退避默认值。
- 增加明确的 `RequestNotSentTimeout` 错误：整个逻辑操作从未进入帧写入阶段。只要任何一次尝试进入写入阶段，期限结束均保守返回现有 `RequestTimeout`（结果未知）；后续重试在队列超时不能把先前未知结果降为“未发送”。业务幂等号和 payload 始终沿用原值。
- 等待许可或写锁超时不注册/遗留响应关联，也不损坏连接。进入写入后失败或取消沿用关闭半帧流的 RAII；等待完整响应结束只释放当前关联，已有复用连接活性判断保留，其他在途响应仍可正常交付。迟到响应由唯一递增 rpc_id 丢弃。
- 使用同一绝对期限约束各阶段，并在拿到许可/锁后再次检查到期，避免一个已到期但立即 ready 的 Future 偷发请求。配置期限必须为正且可表示，不能让 0 意味着无限等待。
- 现有 `ClientRequestTiming.queue_wait/exchange` 和旧 observer 回调保持兼容，排队超时应完整归到 queue_wait；连接尝试继续使用既有观测入口。同步校验/编解码有协议大小限制，墙钟期限不抢占同步 CPU，但不得在校验或排队已经耗尽预算后发包。
- TS SDK 的 Transport 与 TiangZ Host 还需独立衔接；TS SDK 不能通过单独 `Promise.race` 假装撤销 Rust 队列。宿主当前引用已发布 DBProxy tag，联合候选验证要显式选择本地 worktree，不能提交临时路径依赖锁。

### TS 外层预算与 Host 期限

SDK 增加显式 `DbProxyClient.WithRequestBudget(timeoutMs?)`，返回独立作用域客户端，不修改原客户端或其他并发调用；默认使用 transport 声明的 requestTimeoutMs（缺省 5000），正整数 1..120000。作用域使用 transport 的单调时钟，普通 Node 可用 performance.now，裸 V8 由 Rust Host 提供 Instant 时钟。嵌套作用域不能延长父期限。`GetRemainingRequestBudgetMs()` 用于宿主 Repository 控制退避，耗尽时返回保守结果未知超时错误，不继续启动下一请求。

Transport 的现有方法增加可选末尾 `DbProxyRequestOptions { timeoutMs }`，SDK 只有在 transport 明确声明 supportsRequestTimeout 时才允许预算作用域；旧普通客户端调用保留，不让旧 transport 静默忽略新预算。SDK 保留校验和 defensive copy，具体 I/O 取消归 transport；不增加 Promise.race 或重试层。HostDbProxyTransport 在参数转换之前将剩余毫秒固定成 Rust 单调时钟的绝对期限，Rust 取该期限与配置上限的较早值约束已有 OwnedRequest；这样序列化/解析同样消耗预算。网络协议字节和服务端 schema 不变，内部 Host op 签名需随宿主重建。

Repository 的 Load、Save/SaveSnapshot、Enqueue 入口各建立一次作用域，编码、版本校验读取、迁移写回/重读、最多三次 StorageUnavailable 重试及 jitter 消耗同一期限；已存在的 write 对象/请求号在重试之间保持。耗时同步代码与 V8 停顿不可被抢占，但已耗尽后不得再发起 ready I/O。自定义 transport 要先声明并实现预算契约；测试使用明确的受控单调时钟/取消夹具，不伪造支持能力。

联合开发使用显式选择的 DBProxy worktree 生成 npm 候选并在本轮宿主隔离依赖环境验证；现有已发布 tag/锁不通过手工修改切换到本机路径。正式依赖更新属于多仓库发布冻结，候选验证与默认已发布依赖的结果分别记录。

## N：预算盘点与待落实项

### 已实现：Process 入站准入总量

核对生产入口后确认 TCP/Auto/WebSocket 在 accept 后直接创建任务，只有每次握手 5 秒期限而没有任务数量总上限；KCP 已有每端点 65536 Session 上限，但多个端点可以叠加。下一步以一个 Process 共享的 RAII 准入对象覆盖所有生产 backend：`process.network.maxAcceptedConnections`（默认 65536，沿用现有 KCP 数量级）和 `maxPendingHandshakes`（默认 1024，独立的初始保护值），均为 1..1000000 的整数，0 不是无限。两者独立，握手数自然同时受连接总数约束，不静默修改配置。

TCP/Auto/WebSocket 在 accept 后、分配连接任务前尝试同时取得连接/握手名额；超限直接关闭该 Socket，不排队等待名额，不建立额外过载响应队列。完整前导/认证或 HTTP Upgrade 成功后释放握手名额，连接名额由连接任务持有到真实结束；错误、关闭、panic 和 endpoint abort 都通过所有者回收。KCP HELLO/CHALLENGE 保持无 Session 状态，合法 CONNECT 创建 Session 前取得同一连接总量名额；重复 CONNECT 不重复占用。

此处“连接总量”明确指此 Process 所有业务监听端点接受的入站连接及已验证 KCP Session，包含尚未完成握手的 TCP；主动跨进程 Inner 链接、健康 HTTP、数据/出站字节和 KCP 重传缓冲需分别核对，不能宣称这两个字段已经限制全部内存或 Socket。默认值是可配置的初始上限，不能写成容量基准结论；不承诺不同 audience 在共享上限内的公平调度。

验收使用小限额与两个真实 listener：同时未握手达到共享上限时新增连接关闭；首个握手完成后另一个端点可以握手；活动连接仍消耗总连接额度；主动断开/取消/停止后名额归零并可以重新接入。KCP 与流式端点共享上限，非法 CONNECT 不消耗名额。附有限原因计数与当前连接/握手数，Rust/TS/VS Code Schema 同步；Windows 真运行和 Linux 条件编译分别记录。

### N2 慢写配置冻结

新增 `process.network.writeTimeoutMs`：正整数 1..300000，默认 10000ms。默认量级沿用当前 Process 停机宽限 10 秒，但字段独立；它是可调整的初始保护值，不是容量/移动网络基准结论。一次出站批次从成功准入起，到完整交给 TCP/WebSocket 写出完成共用该期限，排队时间不能忽略；KCP 的该期限仅约束进入可靠传输前的宿主排队，不代替 ACK/重传预算。读对端长期停顿会比 0.6.2 更早断开，慢链路部署须显式配置并验证。

开始正常关闭后，全部已入队批次还共享既有 `stopTimeoutMs` 排空期限（与各批次剩余时间取先到者）；不能每批重新获得完整关闭预算。过期即关闭字节流，日志保留未完成的帧数/字节信息，资源守卫在所有路径回收。0 不代表无限，超过范围启动失败。Rust 反序列化/校验、TS 配置类型、VS Code Schema/说明与测试同步修改；这是 0.7 候选字段，旧宿主会拒绝它。

出站记账同步约束：排队及正在写出的批次必须持续占用现有帧数/字节预算；成功、发送失败、接收队列销毁、writer abort 都通过批次资源守卫恰好释放一次，不能靠每个 backend 的手写减计数维护。KCP 转发单帧持有原批次守卫直到最后一帧完成转交，允许保守占用，不能转发后提前释放。保持已有每连接数值和 KCP 共享队列的帧单位；KCP 内部重传缓冲及 Process 总量仍需单独度量与限制。
