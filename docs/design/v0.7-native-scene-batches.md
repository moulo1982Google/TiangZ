# 0.7 Native Scene 批次的共享元数据额度

本批基于 `04d7321`。当前 TS 未提交批次与待回复分别有 65536 项限制，Rust 整包另有共享字节预算；但 Native 每次提交都生成一个 operation Vec、调度槽和期限堆，单批 256 个执行槽并不限制多个批次的总和。完成部分操作后，这些容器的容量仍保留到批次结束，不能把已归还的某段 payload 字节或 TS pending 数量当作元数据总量。

## 冻结的范围与默认值

每个 Process 的 Native Scene 批次共享 **65536 个保留槽位**，沿用已有单批最大项数作为初始总量上限，不增加用户配置或无限值。call/send/sleep 都按原批次项数整批预留；在复制整包、分配 operation Vec、槽与期限堆之前检查。普通格式/条数必须先合法；后续格式、路由、时钟、字节预算或宿主配置检查失败，归还本次预留。

预留一直持有到整个调度 Future 和其批次容器释放，包含未开始工作、实际执行、等待完成通道可用与部分完成后的原容器容量。正常结束、任务取消或 panic 都归还原所有者，旧任务不能归还到新 Process 的同名计数器。此计数有意保守，不是当前活跃 RPC 数量；大批次只剩一个未结束项时仍保留原批次槽数，不通过提前减计数掩盖实际容器。

满额只拒绝新增批次，以现有 `[scene-overloaded]` 错误前缀经 TS flush 传播；不破坏此前已接受批次。已有 send 只保证 TS 接受，Native 提交失败沿用当前提交失败指标，不伪造确认或自动重放事实。正常 Host completion、入站 Disconnect、本地调用期限和独立停机期限不消耗这些槽，不引入等待准入的额外队列。

固定 Process 指标报告保留槽、峰值、容量及被拒绝批次数。TS 未提交/待回复、Rust payload、批次元数据和物理传输是不同所有者；本批不把单批 256 改成全 Process 网络并发限制，也不宣称远端取消、全部 Native 元数据、TS backing buffer、业务堆或 RSS 有界。

## 验证和兼容

先以实际 V8 直接提交合法 Native 批次的反例验证：完成 sink 背压使第一批 65536 个 sleep 的元数据仍保留，此时再提交合法一项必须明确拒绝。该测试直接覆盖 Native 边界，不代表普通 TS 允许创建超过自己的待回复上限，也不发业务网络。随后放开完成通道，原批次无丢失地排空、额度归零，新批次恢复。

小容量 Rust 测试覆盖多批次竞争、拒绝不改变原占用、原子并发峰值与任务取消/失败释放；实际 Native 验证失败回滚、默认最大批次和字节预算独立。最终重新构建，运行含 KCP 完整矩阵，保留真实 65536 单向消息、64 MiB 批次、本地/远程期限、热更和停机原断言；Linux 条件编译与 AI 实际归档另验。

所有权实现留在 `src/host/scene_operations.rs`，桥接负责预留并将守卫交给原调度任务，Process 观测读取同一所有者。不引入通用 Manager 或按函数拆分。两个 VS Code 插件没有新配置、Native schema 或编译规则；AI 指引同步范围与释放时机，插件继续独立版本。内部宿主变化需完整构建重启；没有发布或用户服务变更。
