## 2. 保留的架构契约

1. 一个 OS Process 一个 V8、一个 TS 业务线程；一个 Process 可承载多个 EntryScene。
2. Rust/Tokio 负责网络、分帧、宿主能力和受控的 Rust 权威数据；TS 负责业务编排。
3. Actor 按运行时地址进入自身 mailbox；`ordered` 在跨越 `await` 时仍串行，`unordered` 不获得 TS CPU 并行。
4. Model 定义稳定字段、构造、继承和身份；Hotfix 只替换行为和既有 Handler 绑定。
5. Hotfix 与完整配置作为同一 Process 内的配对候选提交，沿用预检、现有主动暂停、排空、同步提交和失败恢复。默认暂停窗口仍为 3000ms；不新增第二套屏障或无限等空闲机制。
6. 时间驱动业务使用所有者 Timer 和方法名回调，截止时间与恢复状态归 Model；数据库、RPC 等结果等待允许使用 `await`。
7. 保留 Snapshot、可覆盖 latest/Delta、不可静默丢失 Event 的区别；网络写入成功不等于业务事实已持久化。
8. 游戏能力由外置模块承载；业务依赖 Stable 入口，协议、SDK、声明和锁通过正式生成器维护。
9. DBProxy 存储通用记录与提交效果，不解释地图、背包、战斗等玩法。Repository 负责业务 DTO 与恢复语义。

借鉴 ET 的规则检查、明确身份与测试闭环；借鉴 skynet 的资源所有权、退出清理和小核心。具体实现服从 TiangZ 现有契约，不移植其他框架的线程、热更或消息交错模型。

## 4. R：运行时正确性修复

### R1. Timer 异步任务进入既有排空判断

**修改目标。** Process 提交 Hotfix 前，既有范围内的 Scene、Actor、Component 所拥有且已经开始执行的异步业务任务必须全部可见。未来才到期的 Timer 不等于在途 Promise，不能因存在长期 Timer 而永久阻止提交。

**设计约束。**

- 核对所有者 Timer 到 mailbox 到 Promise 完成的完整路径，在现有 ProcessHost/任务统计拥有者处补齐缺口，不建立全局 Promise 猜测器。
- 入队未执行与执行未完成分别统计；同一任务经多层包装不得重复计数。同步完成、成功、异常、取消通知和所有者销毁都必须有明确释放路径。
- 所有者销毁只取消未来调度；已开始的异步工作仍按真实完成处理，不能简单清零计数。
- Timer 到期与 `onCancelled` 都纳入审查。所有者方法名解析、Actor mailbox 顺序和当前错误日志行为保留。
- 暂停超时使用既有恢复旧候选路径；不能把“取消等待”当成“已经撤销业务副作用”，不能因为任务超时而放开 ordered mailbox。

**验收。** 独立 Actor、动态 Scene 内 Actor 和 Component 各有正常/拒绝 Promise 用例；异步未完成时拒绝提交，完成后恢复；取消通知和销毁不漏计、不负计；暂停超时后旧行为仍可继续服务。

### R2. 固定零延迟 Timer 的执行轮次

在 Update 开始前已登记且到期的 Timer 可以本轮执行；本轮回调中新登记的零延迟 Timer 最早在下一轮执行。使用明确的轮次或候选边界表达，不靠给时间加任意 1ms 绕过。

延后的新 Timer 不得挡住本轮原有到期 Timer；取消已登记任务立即生效；重复 Timer 继续跳过错过的周期，不突发补跑。验收覆盖相同 deadline、多层零延迟链、自取消、取消另一个候选和大幅时间推进，使用可控时钟。

### R3. RPC 在所有异常路径释放关联资源

从成功预留 RPC ID 起，后续修改请求、codec 编码、封装 Actor/Trace 帧、发送和解码都必须处于相同的异常释放范围。保留错误类型和调用方可见的响应关联语义。

验收分别让 codec、帧封装、发送和响应验证失败，再执行正常调用；在途集合回到初始值，无错误 ID 复用、旧响应串入新请求或吞掉原异常。该修复不同时重做 RPC API。

### R4. Auto 模式支持分片握手

Auto 识别必须在足够区分协议的前缀到达后作出判断，或在 EOF/握手期限内明确失败。预读字节必须原样交给选定协议，不丢失、重复消费或因部分前缀忙循环。

在真实 Rust listener 上验证 `G`/`ET`、`GE`/`T`、完整 GET、普通 TCP、前缀后断开及一直不发完整前缀。握手期限使用墙钟预算，不能由 TS 游戏 Timer 驱动。现有浏览器 WebSocket 取消测试不能替代此服务端验证。

## 5. N：网络、过载与退出

### N1. 资源预算及超限行为

先盘点已有固定上限与指标，补齐缺失的计数和字节预算，复用现有配置结构。下表是预算所属层，不代表预先冻结新字段名称或任意默认数值。

| 资源 | 所有者 | 必须限制或观察 | 达到上限后的契约 |
| --- | --- | --- | --- |
| 已建立与未完成握手的连接 | Rust listener/connection | 活动数、握手数、握手时长 | 拒绝新增或到期关闭，释放准入名额 |
| 入站帧与宿主批次 | Rust Process ingress | 帧数、字节数、单帧最大值 | 按现有协议背压或显式过载；控制消息有界保留通路 |
| TS Scene/Actor 待处理任务 | mailbox 所有者 | 深度、驻留字节、排队时间 | RPC 返回明确错误；单向事实不能悄悄丢弃后报成功 |
| 发往连接的队列 | connection writer | 帧数、字节数、最老批次等待 | 对可覆盖状态按既有稳定 key 合并；慢连接在期限内退出 |
| 内部 RPC 与 DBProxy 请求 | 对应客户端 | 在途数、等待准入数、等待预算 | 及时拒绝或超时；不无限堆积等待 Promise |

Process 总预算和连接/Actor 局部预算需要组合，不能让大量未超局部上限的对象绕过总量限制。错误响应本身也受预算约束，不能通过“发送过载提示”建立新的无界队列。

默认值沿用有依据的现值；新增上限在实现评审时以基线负载、帧大小和部署内存核定。除非迁移说明明确支持，不能用 `0` 暗中表示无限。调小上限的过载用例必须证明拒绝后可恢复。

### N2. 慢连接和部分写

正常关闭在已有业务通知之后有界排空；超过墙钟期限后关闭 Socket 并记录未写出的帧数/字节。不得为排空永久阻塞进程停机。

0.7.1 补充：写队列已满不再等于慢连接。一轮 Update 为同一连接产生超过写队列（4096 帧 / 4 MiB）的帧时，剩余帧按顺序暂存在 Process 侧（`src/process/outbound_spill.rs`），计入进程出站总预算，每轮先于新帧补交；暂存在 `network.writeTimeoutMs` 内没有任何进展、单连接暂存超过 16 MiB 或进程预算耗尽才关闭。TS 请求关闭时若仍有暂存，等暂存交付后再关闭。0.7.0 发布 CI 曾因“满即关”在 65,536 个挂起 RPC 同时完成时断开读取正常的 Inner 对端。

部分帧已写出后发生超时或取消，关闭该连接，不能继续复用被截断的字节流。移除 writer 表项只是生命周期的一步，还需等待或取消读写任务、释放队列及连接许可，并核对 pending RPC 的终结。

验收使用真实 Socket 的不读对端，覆盖正常关闭、写阻塞、对端断开和进程停止；结束时任务、连接许可和队列统计回到基线。

### N3. Listener 所有权与入口访问

listener 的任务句柄、停止信号和退出结果由 Process 明确拥有。启动过程中部分 listener 失败时回收已启动资源；运行中不可恢复的 accept 失败使相关就绪状态失败并按既有进程退出策略收口，不能仅写日志继续宣称健康。

逐个核对 TCP、Auto、WebSocket、KCP 及启用的 backend：`inner`、`outer`、`mixed` 在连接 admission 与消息分发处含义一致。保留已有帧访问校验；它不能替代连接级限制，网络来源判别也不等于凭据鉴权。未实际验证的平台/协议写入限制清单。

## 6. G：通用框架边界

### G1. 区分地址、目录与空间位置

| 层次 | 范围 | 0.7 决策 |
| --- | --- | --- |
| Actor 地址和 mailbox | 已知运行时地址的投递、连接绑定、旧所有者消息隔离 | 留在 Core |
| 通用目录原语 | 逻辑 key 到当前地址的版本记录、CAS 与操作标识 | 保留现有 `LocationDirectory<TKey,TValue>`；不强制网络部署 |
| 可选目录服务 | 确有动态查址、迁移或接管需求时提供 RPC 入口 | 按需装配，可同进程；默认简单示例无需独立进程 |
| 游戏路由策略 | account/player、Gate 接管、MapHost 分配、换图恢复 | 留在具体模块 |
| 空间位置 | 坐标、地图、AOI、寻路 | 留在具体模块 |

[ActorLocation](../../app/core/process/ActorLocation.ts) 的本地连接绑定与[LocationDirectory](../../app/core/location/LocationDirectory.ts) 的通用目录不是地图坐标服务，也不等于服务健康发现。保留 Stable 导出和已有调用语义；不为改名新增兼容转发层。已持有目标地址时直接路由，不把目录查询插入每条消息的热路径。

### G2. 地图部署配置归属

`staticMapIds`、`acceptDynamicMaps` 的迁移范围包括 TS `SceneConfig`、Rust 反序列化/投影、Schema、示例配置、创建模板及消费方。只删 TS 字段会留下两套不一致契约。

目标为 MMORPG 模块拥有的、按实例关联的强类型部署配置。优先复用现有模块配置/数据包通道，静态内容继续使用模块的正式配置生成链；部署拓扑不能伪装成玩法表数据。

若现有通道不能表达实例关联配置，先列出现有能力缺口，单独评审最小扩展。不能在 `SceneConfig` 增加任意业务 `any` 字典以绕过边界。

迁移采用先提供模块入口和示例迁移、再废弃旧字段的顺序；过渡期双写必须检测冲突。旧字段何时移除由兼容矩阵决定，不能因版本为 0.x 就静默丢弃配置。涉及 Model/部署契约变化须重建并重启。

### G3. 消费方证明

使用现有脚手架构建最小房间式示例：一进程、直接寻址、创建/加入/离开、重连快照、正常停止，不包含 Location/MapHost。示例留在 Examples 或测试夹具。

同时验证现有 MMORPG/SLG 模块的声明、构建与相关运行路径，特别是配置迁移。通过一个简单示例不能替代现有消费者兼容性；引入某类游戏也不能成为扩大 Core 领域语义的理由。

## 7. A：静态检查的统一与覆盖

### A1. 现有基础和接入方式

现有 [verify_runtime_contracts.mjs](../../tools/verify_runtime_contracts.mjs)、[verify_hotfix_boundary.mjs](../../tools/verify_hotfix_boundary.mjs)、[typecheck_game_modules.mjs](../../tools/typecheck_game_modules.mjs) 已使用 TypeScript 语法/类型能力，Developer Tools 的部分规则已经共享。先建立清单，不重复实现第二套检查器。

| 规则 | 当前基础 | 0.7 检查重点 |

每项规则记录唯一规则来源、稳定诊断码、等级、适用文件集合、例外依据、对应正反例和接入命令。对不完整工程或无法证明的动态表达式，区分错误与“无法判定”，不把猜测作为硬拒绝。

业务规则的共享实现优先归 Developer Tools；宿主生成锁、构建指纹和宿主专属集成检查归 TiangZ。不要求两边互相导入源目录。发布版本和测试夹具验证规则一致性，避免插件更新与引擎更新分别改变结论。

编辑器与 CLI 对同一内容、同一项目配置和同一规则版本必须给出相同规则结论；编辑器可以延迟完整类型检查，但不能用不同逻辑判定成功。自动修复只用于可确定无副作用的改法。

## 9. D：TiangZ-DBProxy 服务端与 SDK

本工作包包含 DBProxy 自身代码和 Rust/TS SDK 的改进，不仅是宿主文档。实现分别落在独立 DBProxy 仓库、宿主桥接和 Repository 消费方，保持通用 payload/CAS/回执/提交效果边界。

### D1. 多租户共享监听配置一致性（P0）

**问题。** 单个共享 listener 的并发上限取首租户配置；若租户声明不同值，可能出现声明与实际执行不一致。认证隔离与存储隔离不能解决此配置问题。

**0.7 配套决策。** 先把 `maxInFlightPerConnection` 明确为共享 listener 的一致性字段；校验所有租户值相同，不同就拒绝启动并指出字段及租户标识，不能静默取第一个、最大值或最小值。保留现有按租户连接配额和认证绑定。

不在本轮顺带实现租户公平调度器。未来确需每租户在途限额时，再把配额挂到认证后的租户所有者并设计总量上限。

**验收。** 两个租户不同并发值、调换配置顺序都在启动前失败；一致配置正常启动；同 RecordKey、同操作 ID、重连与连接配额仍隔离；诊断不得包含 token。直接创建 `ServerConfig` 的调用也需审查其配置范围。

### D2. 端到端请求预算（P1）

DBProxy 已有 PG 连接排队预算、重连冷却和缓存操作预算，详见[PG 请求预算](../../../TiangZ-DBProxy/docs/postgres-request-budget.md)。本项补齐 SDK 与宿主层，不重复实现已有存储预算。

拟将单次 SDK 请求预算从 API 接受调用时开始计时，覆盖等待在途名额、等待写锁、写入和响应。拿到锁后不能重新得到一整段预算；底层阶段期限为剩余总预算与原阶段上限的较小者。

宿主调用和显式重试协调者拥有更外层操作预算；客户端切换 endpoint、退避与再次排队都扣除同一操作的剩余时间。不同进程不传递本机单调时钟绝对值，跨边界只传剩余时长或经评审的协议上下文，不能假定机器时钟完全同步。

这是超时可见语义变化：原本长时间排队后还能发送的调用可能提前失败。保持已配置值的可解释性，写清迁移、错误分类和默认值来源，不偷偷扩大旧 timeout 来掩盖问题。

| 失败阶段 | 调用方可以知道什么 | 资源处理 |
| --- | --- | --- |
| 等待准入，尚未发送 | 本次调用尚未提交给服务端 | 不发送，释放本次许可与注册 |
| 部分写、写完后断开、等待结果超时 | 业务结果可能未知 | 保留幂等身份；部分写关闭流，不能直接重用 |
| 收到明确业务错误 | 按错误契约解释 | 释放关联资源，不把冲突当基础设施故障盲重试 |
| 已确认提交，响应丢失 | 可能通过同操作重试或已有查询恢复首次结果 | 不生成新 ID，不重新计算随机结果 |

取消 future 或调用方超时不保证服务端事务回滚。迟到响应只能丢给已结束关联，不能污染其他在途请求；一条慢请求也不能无条件中断仍健康的整条复用连接。

**验收。** 锁住许可、写锁、存储连接分别验证预算；记录 queue/write/response 耗时与总耗时；超时后等待集合、permit、pending ID 回到基线；并发正常请求继续完成；重试累计不超既定预算及允许的调度误差。

### D3. 幂等、写入模式与恢复契约（P1）

保留默认权威读取与显式缓存读取的区别；配置了持久化后，数据库故障不能静默切到内存。

| 接口/模式 | 保留语义 | 需要验证的使用约束 |
| --- | --- | --- |
| 普通 CAS 保存 | 版本匹配后写入，同请求号重试恢复既有结果 | 请求 ID、记录身份和 payload 指纹保持一致 |
| `SaveMultiSnapshot` | 多条独立结果，允许部分成功 | 调用方逐条处理，不能把批量当事务 |
| `ApplyMultiTransaction` / `CommitRecords` | 同一数据库范围的原子提交 | 超时恢复首次完整结果，不能重新生成效果字节 |
| queued 写 | 按确认档位接受可靠队列写，后台推进落库 | queued sequence 不能保护所有混合写；同一键的 direct/queued 模式需明确边界 |
| Outbox | 至少一次投递 | 消费者按稳定事件身份去重，业务效果与 inbox 必要时同事务提交 |

审查 TiangZ Host、Rust SDK、TS SDK、Repository 是否各自重试，合并重复的重试责任；总预算与操作标识由明确的一层拥有。恢复路径不得二次扣费、重抽结果或用新操作号掩盖原结果未知。

真实验收覆盖事务提交成功但 ACK 丢失、同 ID 同 payload 重放、同 ID 不同 payload 拒绝、批量部分成功，以及 Outbox 重复投递的消费方处理。内存后端的通过不能替代 PostgreSQL 事务验证。

### D4. 回执保留与容量治理（P1 设计和观测，自动删除单独评审）

DBProxy 已有[记录删除与幂等回执保留期设计稿](../../../TiangZ-DBProxy/docs/record-deletion-and-receipt-retention.md)，状态仍为待评审、未实现，涉及删除墓碑、普通回执清理、迁移和协议变更。本项继承该稿的现状证据并做安全评审，不重复从零设计，也不把其中的默认保留天数视为已经冻结的生产契约。

本轮先交付各类回执/事实/Outbox 表的所有权与用途清单、行数/字节/最老时间的可控频率观测、增长与备份容量说明。昂贵统计不能进入每次请求或每次 scrape 热路径，不暴露记录 key/操作 ID 为指标标签。

默认不自动删除幂等回执。仅设置 TTL 会使过期旧请求重新执行；归档也不天然解决在线去重问题。账本事实、未确认 Outbox、死信和幂等回执不能使用一个通用清理开关。

启用清理前必须有：可执行的重试期限与退休边界、删除后仍拒绝旧操作的机制或可查询归档、与在线写并发的安全条件、可恢复的分批执行方式，以及旧客户端兼容说明。当前这些条件未冻结，不能承诺“保留 N 天后安全删除”。

如果只完成策略和观测，验收结果就明确写成“无自动清理”；后续清理工具不能借 0.7 配套改进名义直接运行在现有数据库。

记录删除及墓碑物理回收单列候选：必须验证迟到缓存回写、旧 queued 数据、重建后的 revision ABA、超保留期盲写、既有事务回执查询和混版本服务端。仅凭当前 backlog 年龄较短不能证明所有旧请求永久失效。删除 API/墓碑迁移若纳入 0.7，需要另行冻结该已有设计，不能作为本项顺带实现。

### D5. 配套发布与存储验收

DBProxy 修复独立建立开发分支和提交，协议、服务端、Rust SDK、TS SDK 的变化保持同步。无协议变化时不改指纹；发生协议变化时先完成兼容评审和正式生成，不手改生成物。

依赖关系为：DBProxy 服务端与 SDK 修复及独立验收 → 明确兼容范围并发布 tag → TiangZ 更新依赖与锁 → 消费方联合验收。纯内部兼容修复无需人为引入不兼容；确有协议/schema 变化时按已验证的服务端先行升级顺序部署。

本地跨仓库开发使用既有未跟踪配置覆盖；不能提交指向本机 sibling/worktree 的路径依赖。不要为了宿主版本同步而无依据修改 DBProxy、Examples 或工具的版本范围。

## 10. O：诊断信息与指标

复用现有 Logger、Trace、健康接口和 Prometheus 导出；先核对现有指标，再补缺失项。

| 场景 | 最少需要回答的问题 |
| --- | --- |
| 请求变慢 | 等待发生在准入、mailbox、写锁、网络响应还是 DB 阶段？ |
| 过载 | 哪一级预算耗尽，当前值/上限是多少，采取了拒绝、合并还是关闭？ |
| 热更未提交 | 当前阶段、阻止排空的任务类别、剩余期限、失败后活动版本是什么？ |
| 停机未完成 | 哪个 listener/connection/task 未退出，是否进入有界强制关闭？ |
| DBProxy 结果未知 | 是发送前失败还是发送后不确定，调用方需要恢复哪个操作？ |

指标标签只使用有限进程/服务类型、阶段、原因枚举；连接 ID、Actor ID、账号、RecordKey 和操作 ID 不进入标签。必要的关联身份进入受控日志，凭据和完整业务 payload 不输出。

新增计数必须覆盖成功与失败释放路径；日志限速不能丢掉最终汇总。验收包含过载后计数归零、异常原因可关联，以及指标格式拆分前后的名称、类型、转义和 histogram 等价。

- 适用平台 Windows/Linux 的构建与核心网络回归通过；实验 backend 或其他平台单独说明覆盖范围。
- 队列峰值不超过配置，结束后连接/permit/pending 归位；没有未处理异常、错配响应或已确认业务效果重复。
- 负载比较在相同机器、配置和制品条件下进行，先预热、至少三轮。性能与资源增长阈值在测量前冻结，不能根据结果放宽；没有匹配基线就先建立基线。
- 小型消费者和现有模块兼容性通过，升级文档、Stable 声明锁、协议锁及模块宿主范围一致。
- 两个 VSIX 的实际打包/隔离安装、共享语言核心与宿主 codegen 对照，以及 AI 分发包与规则维护源一致性通过；只修改源码不算完成插件交付。
- 完整验收包括经单独安排的持续负载与恢复证据；此前版本的长稳和短测不能替代。未取得这部分证据时明确标记尚未完成生产质量验收。

## 12. 兼容性、升级与回退

| 改动 | 升级要求 | 回退边界 |
| --- | --- | --- |
| Core/Model 源码、文件布局 | 完整构建、部署、Process 重启；Hotfix-only 拒绝旧冻结身份不匹配 | 回退匹配的宿主、Model、Hotfix 与配置制品 |
| 地图配置归属 | 模块支持先行、示例迁移、冲突检查和废弃期说明 | 旧配置路径仍受支持时可回退；不能默默恢复失效字段 |
| 预算和超时行为 | 给出原默认值、适用范围、迁移后可能提前拒绝的案例 | 仅回退已验证配置/版本，不把无限预算作为故障处理 |
| 静态规则强化 | 每条新增阻断提供迁移样例与正反例 | 无法确定的分析不擅自升级成阻断；不提供通用跳过开关 |
| VS Code / AI 插件 | 发布兼容清单，固定规则/语言/生成器版本，验证实际安装产物 | 旧插件可提示升级但不能错误地接受新契约；插件回退不改业务状态或源码 |
| DBProxy/SDK | 固定已发布依赖，验证协议和存储迁移兼容矩阵 | 数据迁移不自动逆向执行；无法回退的版本边界事先说明 |

联合 Hotfix 回滚只恢复行为与配置，不倒退已提交的玩家/业务状态。DBProxy 服务回退也不能删除已提交事实或伪造旧回执。

## 15. P：两个 VS Code 插件与 AI 插件

### P1. Developer Tools：需要修改

该插件已经提供 AST 诊断、配置 Schema、模块导航和项目任务入口。0.7 以完善这些入口为主，不另建一套与 CLI 不同的规则。

**明确修改项。**

1. 将 A 工作包确认的共享规则、诊断码、正反例接入编辑器、CLI 和模块构建，区分支持的宿主版本与规则版本。
2. 跟随 G2 更新 `extension/schemas/process-config.schema.json`、`known-scenes.schema.json` 等实际相关 Schema、Hover 和创建模板。过渡期旧地图字段的提示与宿主迁移策略一致，不能在宿主尚接受时无说明地硬拒绝，也不能让插件继续生成宿主已废弃的字段。
3. 识别已确定的预算、超时和 DBProxy 配置；字段默认值、单位和作用域来自同一配置契约。支持 JSON Schema 诊断的字段不在 TS 规则里再维护一份冲突逻辑。
4. 多根工作区及多个宿主 worktree 并存时，明确展示选中的宿主与项目根，任务 cwd、生成器、Stable 类型与 System 声明使用同一宿主。清理/停止只作用于插件为该项目启动的任务，不能误操作另一工作树。
5. 更新 Timer/Hotfix/持久化操作的说明和设计向导，解释结果未知、幂等重试及可选目录寻址。引导使用实际已有 API，不自动为通用游戏创建 MapHost/Location。

**实施位置。** 优先复用 `packages/project-core` 的工程模型/诊断、`packages/design-core` 的确定性设计规则、CLI 和 `extension` 的展示适配。完整 Program 的类型分析需要有界缓存及关闭项目后的释放；不能为每次按键全量启动新的编译进程。

**验收。** 相同夹具在 CLI 和 Language Server 返回相同诊断码与源码区间；缺少、多个和错误的宿主路径都有清楚结果；带空格路径任务可执行；旧 0.6.2 项目与 0.7 项目并存时不串诊断和生成输出。正常打包 VSIX 后在隔离用户数据/扩展目录中验证 Problems、Hover、Schema、项目检查与任务停止，不覆盖正在使用的开发插件。

### P2. Native Language：需要兼容核对与配套修改，语法变化按契约决定

当前工作树的语言核心为 0.17.0、扩展为 0.16.0，而 TiangZ 基线依赖语言核心 0.16.0。这个差异必须进入联合版本清单；不能只看到插件版本较新就判定与宿主生成器兼容。

**明确计划。**

1. 盘点语言核心与宿主实际使用的 Parser、Validator、codegen API，确定 0.7 采用的发布版本；对照已有 `@persistent`、`@transient`、`@queued`、`@transactional` 的生成结果及写法限制。
2. 若 D2/D3 改变 Repository/SDK 调用形状，同步修改生成核心与宿主适配，并由正式 codegen 生成；验证输出的 TS/Rust 可编译、依赖当前 Stable API、重试保留原身份。不能只修 Hover 而让生成代码仍调用旧 API。
3. 编辑器补全、Hover、Snippet、错误说明与实际语言/持久化契约一致；不能建议同一记录混用 queued 与 CAS/事务写，也不能以清空数据库作为生产迁移路径。
4. codegen Task 的项目根、输入集合和工具版本要显式归属当前工程；多 worktree 下不得向另一宿主的 Generated 目录写入。
5. 保留现有输入限制、有界缓存和 Language Server 性能测试。无语法/语义变化时不为宿主 0.7 重写 Parser；异步 Native op、删除标记等候选未获设计结论前不加入补全或生成器。

**验收。** `.native` 同一夹具在编辑器和宿主 codegen 中结论一致；非法写法/重复身份有确定性反例；生成代码通过当前宿主构建及目标持久化行为用例。记录 Core 与 VSIX 两个版本和实际包内的语言核心身份，不能要求它们版本号相同来替代兼容检查。VSIX 打包后在隔离编辑器中验证诊断、导航、生成任务和大文件输入限制。

### P3. AI Plugins：需要修改维护源、清单与分发包

维护源仍是 TiangZ 的 `tools/ai-assistants/skill`、`tools/ai-assistants/cindy` 和 `docs/ai/skill-development-contract.md`。`TiangZ-AI-Plugins` 保存 Codex/Claude 技能分发、Cindy 源码/包和插件清单；维护源与分发仓库各自的 worktree 必须在同一次兼容发布中对应起来。

**规则内容。**

- 框架定位：通用 Actor 寻址与 MMORPG 迁移分开，简单项目无需默认 Location 拓扑。
- 代码组织：按职责克制拆分，保留所有者与生命周期，不按行数硬拆或引入只转发层。
- 正确性：沿用 Model/Hotfix 配对发布与 3000ms 窗口，说明任务真实完成、超时、取消与副作用的区别。
- 持久化：总预算、同操作重试、批量部分成功、原子提交和 Outbox 语义；回执/删除方案以已评审能力为准。
- 协作：区分讨论、设计文档、实现和测试阶段；用户要求先讨论时不把补充任务当成开工。多 worktree 先确定目标，不根据目录邻近关系自动切回主线。
- 证据：静态阅读、规则检查、真实网络、真实存储和长稳分层；计划、部分通过或中止都不写成最终验收通过。

**分发流程。** 先改 TiangZ 工作树内的维护源，通过既有 `build.mjs` / `check.mjs` / `build.mjs --check`，再把对应生成物定向同步到 AI Plugins 工作树。Codex/Claude 共享技能与 references 保持一致；Cindy 规则目录和实际工具返回一起核对。

插件 JSON、marketplace、MCP 配置和包版本按真实文件复核，不假设全部由生成器更新。Cindy 重新打包后核对包内源码/版本/哈希；`.mcp.json` 的命令在目标 OS 和隔离 PATH 上验证。只有明确选择安装环境后才做真实安装，不改当前全局插件缓存。

开发生成使用当前 worktree 的 `dist/ai-assistants`；默认不使用会改上层已安装技能的 `--workspace`。不能把源码改完或重新生成 dist 等同于“用户已经安装新插件”。运行中从仓库读取的约束优先，离线参考标明版本；AI 建议不能覆盖编译器和确定性检查。

**验收。** 技能结构、规则 ID、随包 references、JSON 和源码/分发一致性通过；真实打包产物可加载。Codex/Claude/Cindy 各在具备客户端的隔离会话中执行同组只读场景，检查实际使用的工作树和规则版本；缺少某客户端则如实列为未验证。新增协作场景包括“仅讨论不实施”“仅写设计稿”“选择 0.7 宿主”“DB 超时结果未知”，不能只检查提示文案含关键词。

### P4. 插件与宿主的联合版本和发布顺序

兼容记录至少包含：TiangZ/DBProxy 提交与发行版、Developer Tools Core/VSIX、Native Language Core/VSIX、AI 维护源提交/分发提交/包版本、Examples 提交、Node/TypeScript/VS Code 版本及协议/生成指纹。VS Code 使用自身 TS 版本与项目 TS 版本时的支持范围要明确测试，不能只测一个开发环境。
