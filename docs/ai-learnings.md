# AI 助手学习笔记 —— 从 TiangZ 项目中学到的架构与工程经验

日期：2026-07-29
来源：Cindy 在对话中对 TiangZ 仓库的性能数据反推与实测对比

## 一、性能估算的教训

Cindy 最初仅凭硬件和架构描述估算性能，结果与实测数据偏差显著：

| 指标 | Cindy 估算 | 实测 | 偏差 |
|---|---|---|---|
| 裸 RPC 吞吐 | 5-8 万 req/s | 27-30 万 req/s | 低估 4-5 倍 |
| 单 Map 同屏容量 | 500-2000 人 | 3000+ 人（CPU 50%） | 低估 1.5-6 倍 |
| V8 GC 健康度 | 担心抖动 | Heap 44MB、预热后零增长 | 过于悲观 |

**根本原因**：Cindy 用了"纯 TS Actor 模型"的经验值，忽略了三个关键设计的乘数效应：

1. **Rust Native 数据权威存储**：高频跨帧实体数据（位置、移动）下沉到 Rust Arena，TS 只持有 generation handle。移动快照在 Rust 侧批处理并直接编码，完全绕过 V8 主线程。
2. **广播 single-flight + revision Ack**：同帧 dirty 状态合并为一次广播，前一批未完成时保留最新 revision，发送成功后按 revision Ack。3000 人场景下 frames/batch 达 2269，平均广播仅 9ms。
3. **多 Gate 进程分摊连接**：16 个 Gate 进程分散在多核上处理 TCP 连接和下行编码，MapHost 只发 M2G 跨进程消息，不直接面对 3000 个 socket。

**教训**：估算游戏服务端性能时，必须逐链路区分"哪些数据走 TS/V8、哪些走 Rust 原生批处理、哪些被多进程分摊"，不能只看"V8 单线程"就拍脑袋给数字。

## 二、值得学习的架构决策

### 2.1 Model/Hotfix 硬边界

- Model 承载字段、构造、继承、状态默认值，随进程启动加载一次，运行时不可变。
- Hotfix 只承载方法实现和 Handler 绑定；`@hotfixFor` 类不得声明字段、构造函数、静态初始化块或改变继承关系。
- 不做在线字段 migration —— 需要迁移就说明 Model 变了，走版本化部署和进程重启。
- 热更是整个 Process 的 TS 行为世界事务，不是单个 Scene 的局部替换。
- 候选 Bundle 在隔离 V8 中做语法、协议指纹、Stable API 和 Native schema 兼容预检。

**为什么值得学**：绝大多数游戏服务端的"热更"最后都变成一团浆糊。从第一性原理锁死"什么可以热更、什么绝对不行"，比后期打补丁成本低得多。

### 2.2 Rust 与 TS 的数据分工原则

- 普通业务数据默认用 TS Component。
- 只有数据量、访问频率、批量编码或热更状态所有权存在明确收益，且开发者同意后，才下沉 `.native` 原型。
- 下沉后固定链路：`TS -> generated Fast Op -> Rust Entity Store`，Rust 不回调 TS 读权威状态。
- 不在 Update 中逐实体逐字段跨边界扫描；批量处理设计粗粒度 op。

**为什么值得学**：避免了"什么都往 Rust 塞"和"全留在 TS 卡死"两个极端，用明确的决策标准代替个人偏好。

### 2.3 协议与状态同步三层语义

- **Snapshot**：进入、重连、主动全量同步。
- **Delta**：相同稳定 key 可覆盖的状态（`latest` 策略）。
- **Event**：技能、道具、掉落等不可丢失事实（`event` 策略，不得静默覆盖）。
- **Audience 决定发给谁，descriptor 决定如何排队和合并，两者解耦。**

### 2.4 Mailbox 串行模型

- `ordered` mailbox：Handler 跨越 `await` 时仍保持同一 Actor/Scene 串行，避免竞态。
- `unordered` mailbox：允许异步重叠但不获得多线程并行（V8 单线程限制）。
- Actor 通过 `InstanceId` 直接定位 mailbox，不遍历地图查找。

### 2.5 固定帧 + 追赶

- `fixedUpdateMs=50`（20Hz），`maxCatchUpSteps=2`，帧预算硬约束。
- 这要求每帧业务逻辑必须在预算内完成，single-flight 广播等机制都是为这个约束服务的。

## 三、工程实践亮点

### 3.1 性能回归门禁

- `perf/gate` 统一微基准、框架链路、完整链路三层测试。
- 基线按 OS、CPU 标识、Runtime profile 和参数保存，不跨机器直接比较。
- 吞吐/p99/错误三阈值判定，错误零容忍。
- 更新基线必须 `--reason` 显式命令，生成旧值、新值、变化百分比和原因模板。
- `npm run verify:perf` 回归时非零退出码。

**为什么值得学**：性能门禁不是"跑个分看看"，而是带机器指纹、带原因记录、带零容忍策略的工程化流程。

### 3.2 跨平台发布收口

- Windows/Linux 同名 `verify:quick` 和 `verify`，平台差异只在 Backend 专项。
- Rust固定1.97.1，Node/npm固定主版本；这里记录的是当时Release收口阶段的lockfile + `--locked`/`npm ci`做法。当前仍处于开发阶段，默认允许依赖与版本副本迭代，准备正式Release时再恢复这套冻结门禁。
- Release 一键生成双平台制品、默认配置、SHA-256，并在解压目录执行 smoke。
- 依赖审计零 advisory，漏洞例外必须带负责人、原因和到期日期。

### 3.3 AI 协作的正确姿势

TiangZ 项目用 AGENTS.md + docs/ai/ 给 AI 助手提供了极其精确的约束：

- 架构世界观（Process → EntryScene → Scene → Actor → Component）。
- 各目录的职责和默认是否修改的表格。
- Model/Hotfix 硬边界规则。
- 协议帧格式和同步语义。
- 最低验证命令矩阵。
- "可信顺序"：运行中的代码与测试 > 文档 > 路线图 > 历史计划。

**教训**：AI 辅助大型项目时，精确的架构约束文档比"让 AI 自由发挥"效率高一个数量级。AGENTS.md 不是写给人看的 README，是写给 AI 看的"宪法"。

## 四、Cindy 今后应该记住的

1. **估算性能前先画数据链路图**：区分 TS 路径、Rust 原生路径、多进程分摊路径，再给数字。
2. **对 Rust + TS 混合架构，重点关注数据所有权边界**：谁持有权威数据、谁做批处理、谁做编码，决定了实际容量。
3. **V8 单线程不等于单线程瓶颈**：如果高频数据下沉 Rust 且广播批处理在原生层完成，V8 只做业务编排，容量可以远超纯 JS 经验值。
4. **热更设计要从"什么不能热更"开始**，不是从"什么能热更"开始。
5. **性能门禁必须带机器指纹和原因记录**，否则基线无意义。
6. **给 AI 的约束文档越精确，产出质量越高**——这是 TiangZ 项目最值得推广的元经验。
