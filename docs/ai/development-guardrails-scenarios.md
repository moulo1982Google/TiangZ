# AI 开发判断场景

这些场景用于技能/设计工具行为核对，不是实现代码模板。规则源见 [开发约束](skill-development-contract.md)，工程方案见 [开发检查设计](../design/development-guardrails/README.md)。

## 场景与可观察结果

| 输入场景 | 应作的判断 | 应要求的证据 | 错误结论 |
| --- | --- | --- | --- |
| Model 导出一个 `Object.freeze(new Set(...))`，类型检查通过 | 冻结不改变非法导出原型，使用真实 Model 入口校验 | 宿主 `check_module_model_exports.mjs` 或项目 `check` 的结果，含模块与路径 | “类型通过即可启动” |
| Component 构造函数导出，实例字段有 Map/Set | 实例状态不受导出集合禁令限制，不批量改成数组 | 正例真实导出校验和受影响生命周期检查 | “所有 Set/Map 禁用” |
| 保存相同列表，但此前提交尚未确认 | 先以原 ID/字节恢复 pending，再按恢复后状态规划 | 无变化操作与 pending 交错、结果仍未知反例 | “相同值直接成功” |
| A 提交后又提交 B，重建后重发 A，当前值恰好相同 | 按这个操作的历史回执契约处理旧 ID | 受控 Store 与真实 DB 回执，不能只测内存缓存 | “内存中没有回执所以是新操作” |
| 单玩家扣费跨 await，还有其他玩家的请求 | 同一玩家 ordered 有价值，不同所有者不必合并串行 | 同玩家交错与多所有者独立测试 | “遇到 await 全改 unordered” |
| Directory 同时有短超时登记和数据库读写 | 分析串行范围；独立控制 Scene 或 unordered 按键锁都可能合适 | 同键互斥、不同键并发、控制请求穿插，保留共享状态检查 | “框架自动选对锁”或通用吞吐固定某数值 |
| 服务端直走很久才推样本，客户端声称自行预测 | 双方共享速度/时间/单位类型与恢复契约；用真实样本核验消费 | 服务端样本到真实客户端的逐帧比较、目标运行 | “服务端注释就是前后端契约” |
| Node 用例、客户端构建成功，但目标客户端报错 | 核对实际编译片段和目标生命周期，再判断来源 | 原失败、真实产物、反例与目标点击/重连 | “构建成功等于 UI 通过” |
| 文档称已有新 API，但目标 checkout/包身份未知 | 核对声明宿主和实际解析包；未知保持未知 | 宿主/依赖锁/清单与当前代码身份 | “工作目录名/版本号相同即兼容” |

## 评估方法

先给模型一个场景、当前技能和最低必要原始材料，记录它实际读取的文档、工具调用、设计判断与最终声明。判断以上语义是否符合，不要求逐字复述。

规则字符串/归档一致性检查只证明制品；实际模型场景评估单独记工具、模型身份（能证实时）、范围和结果。没有运行模型评估、客户端安装或真实数据库时分别记录未执行。具体数值、namespace、端口和清库政策仍来自目标游戏约定。

P0 本轮只更新维护源与生成验证；Developer Tools MCP 规则同步、正式分发和已装客户端验证属于 P1，不把源文件修改报告成三端已经更新。
