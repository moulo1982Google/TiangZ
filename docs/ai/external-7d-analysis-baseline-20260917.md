## 优先调查：5 次落后读取

Markdown 给出三个累计增量窗口：soak elapsed 约 392648.5s（+1）、470410.3s（+1）、496690.9s（+3）。它们首先是采样定位线索，不应直接当作每个请求的精确发生时刻。

竞争假设（均未证实）：

1. 服务端缓存、缓存修复或切换路径确实返回了落后于契约要求的版本。
2. 测试读请求与写请求并发：读先发起，写随后确认，读返回时却与更新后的本地版本比较，造成时序误判。
3. 不同 API 的 ACK 承诺与测试断言不匹配，例如接收确认与可读提交确认被混用。必须以该部署版本的实际契约为准。

每次需要还原：实体/键、操作号、写版本、ACK 类型及到达时间、读开始/结束时间、读返回版本、读写端点、故障类型和切换时刻，并检查测试器如何取得比较基线。

若要求的是“成功写确认之后新发起的读不得落后”，就必须证明请求先后关系满足这个前提。若确认违反契约，数量少不能豁免；若测试断言有误，需要保留原始失败并用修正后的测试复核，不能删除计数或放宽阈值。

目前只有一致性计数导致 soak 验证失败的证据，不能据此推导“最终数据库仍缺 5 笔数据”或“5 个玩家资产丢失”。还需检查最终对账实现是否因该计数提前退出，以及是否真正完成持久层资产核验。

### 排除一个测试误报假设

`src/bin/dbproxy_fault_soak.rs` 的 `run_player` 逐个 await 读取、事务和交易；每个玩家独占一个 `PlayerState`。`observe_direct_snapshot` 持有不可变 state 引用，比较期间没有其他任务更新其 `direct_revision`。独立 enqueue worker 操作的是另一条 queued 记录。

因此第一轮提出的“同一玩家读未返回时本地确认版本被并发更新”假设不适用于这份代码。`direct_revision` 是收到 Applied/Duplicate 后更新的，下一次读发生在该确认之后。此结论不等于排除了 SDK 或服务端所有潜在错误。

该版本 `crates/dbproxy-storage/src/lib.rs` 的路径：

1. `AsyncTransactionalStore::apply`（约 3783 行）先提交 PostgreSQL。
2. `synchronize_committed_cache`（约 3004 行）缓存更新失败只记录日志并返回，随后 apply 仍返回成功。
3. `AsyncSnapshotStore::load`（约 3611 行）对 Fresh 命中直接返回；Stale 命中也返回旧值并安排后台刷新。
4. 因此，若缓存更新失败而旧值仍可读，修复前存在“已确认新版本，读取命中旧版本”的路径。缓存不可用时回源 PG，不等于缓存恢复后所有可读值都已经最新。

判断：缓存更新失败后的读取一致性缺口是高置信原因方向，代码路径与五个精确键/版本的日志相互支持。该版本文档也要求 read-after-write 和旧读零容忍。尚未做确定性故障复现，也未拿到每次读响应的缓存来源/端点，不能宣称完整根因闭环或已修复。

### 修正“最终对账是否执行”的未知项

main 先 await `validate_final_state`，只有该检查成功，才调用 `validate_observed_consistency`。本轮最终错误正来自后者，所以可以确认前者通过；并非因旧读计数而跳过最终状态检查。

但 `validate_once` 范围有限：逐玩家通过 DBProxy 检查 direct revision、queued sequence 不低于最后确认值，以及最后一次 trade 的版本和状态。它不直接绕开 Redis 查 PostgreSQL，不核对 direct payload，不穷举所有历史交易和账本，也不在此函数验证全部队列排空。因此应表述为“最终客户端可见状态检查通过，运行期旧读检查失败”，不能称为完整持久层资产对账通过。

### 测试工具的确定不足
